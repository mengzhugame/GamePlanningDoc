# AI 代码 Agent 协作工作流

## 来源: `10_流水/Openclaw知识库文件/ai_coding_agent_workflow.md` · 提取日期 2026-05-26

## 1. 核心判断

AI 编程已经从“补全代码”进入“能读仓库、拆任务、改多文件、跑测试、迭代修复”的 Agentic Coding 阶段。个人开发者最容易踩的坑不是不会用 AI，而是把大任务一次性丢给它，最后得到一堆互相不认识的改动。

最稳的工作流是：

```
Spec → Plan → Code → Test → Review → Integrate
```

先把需求写成小规格，再拆成 3-5 个可验证任务。每次只交付一个小功能或一个 bug 修复，跑完验证再继续。

## 2. 五种 Agent 设计模式

| 模式 | 适用场景 | 使用提醒 |
| --- | --- | --- |
| Prompt Chaining | 文档处理、需求到计划、计划到实现 | 每步输出要能被下一步直接使用 |
| Routing | Bug、功能、重构、测试分流 | 先分类，再交给对应流程 |
| Parallelization | 多文件阅读、独立测试生成 | 只并行没有共享写入冲突的任务 |
| Orchestrator-Workers | 复杂编码项目 | 主 Agent 负责架构和集成，子 Agent 做局部任务 |
| Evaluator-Optimizer | 代码审查、性能优化、提示词迭代 | 评审标准要明确，不然会循环空转 |

对个人游戏项目最有用的是 Orchestrator-Workers：主 Agent 管上下文、计划、验证和集成，局部任务再交给专门 Agent。

## 3. 独立游戏开发的落地流程

| 阶段 | 产物 | 失败信号 |
| --- | --- | --- |
| 需求讨论 | `spec.md` 或任务说明：目标、边界、数据模型、验收 | 只说“做一个系统”，没有验收 |
| 规划 | 3-5 个小任务，每个任务可测试 | 一次改十几个文件 |
| 实现 | 单个功能或 bug 的最小改动 | AI 自己发明不存在的 API |
| 验证 | 测试、Play 模式检查、日志、截图或真机结果 | 改完只看编译通过 |
| 集成 | 更新文档、记录工程约定、准备提交 | 修完但没有写下新约束 |

对 Unity 项目尤其要把 Inspector、Prefab、ScriptableObject、Layer、Tag、Database 注册写进 spec。很多 bug 不在 C#，而在编辑器侧配置。

## 4. 上下文工程比模型选择更重要

高质量 Agent 协作依赖稳定上下文：

- `AGENTS.md` / `CLAUDE.md` 写清项目规则、目录边界和禁止操作。
- README 写清模块入口、运行方式和常见坑。
- 复杂系统要有接入清单和测试清单。
- 关键架构决策写进知识库，不要只留在聊天记录。

每次失败的 Agent 循环都会消耗时间和 token。与其反复纠错，不如在任务开头给出真实文件路径、验收标准和不能动的边界。

## 5. 质量控制纪律

1. 不要盲信 AI 输出，尤其是 API、包版本和 Unity 生命周期。
2. 超过 5 个文件的改动先拆任务。
3. 每个任务完成后立刻跑最小验证。
4. 小步提交，便于回滚。
5. 要求 Agent 说明它改了什么、为什么改、如何验证。

## 6. 对《光与朽》和后续项目的用法

- 新功能：先写塔/怪/技能的数值、行为、表现、数据表和验收，再实现。
- Bug 修复：先拿日志和复现步骤定位，不让 AI 猜。
- 重构：先写“不改变行为”的验收，再拆小步。
- 美术/音频接入：把 Prefab、资源路径、Inspector 引用和 fallback 规则放进 checklist。

AI Agent 最适合放大明确任务，不适合替代产品判断。人负责方向和验收，Agent 负责上下文内的执行。

## 7. 常驻上下文要短，专项知识要拆出去

`CLAUDE.md` / `AGENTS.md` 这类入口文件的职责是让 Agent 冷启动时知道“这是什么仓库、去哪看、怎么验证、哪些边界不能碰”。它不适合承载所有失败经验和临时规则。

可复用分层：

| 层级 | 放什么 | 不放什么 |
| --- | --- | --- |
| 入口文件 | 项目目标、目录地图、验证命令、长期硬约束 | 一次性事故、局部模块细节 |
| settings | 权限、默认模式、工具开关 | 项目知识 |
| skills / 专项文档 | 只在特定任务触发的 SOP | 每次都塞进上下文 |
| 模块 README | 局部架构和接入说明 | 全局规则 |

判断一条规则是否进入口文件，先问三句：是否全局、是否长期、是否所有任务都该遵守。三条都满足再写进去。

## 8. Debug/Fix 必须先有复现和验收

让 AI 修 bug 时，不能只说“修一下”。更稳的闭环是：

```
原始日志/复现步骤 → 定位根因 → 写失败测试或最小复现 → 修复 → 跑相关验证 → 失败继续修
```

关键纪律：

- 原始报错栈、CI 输出、测试日志优先于人的二手摘要。
- 小 bug 可以直接做；多文件重构必须先 Explore → Plan → Implement → Verify。
- 不要 suppress 报错来“绿测试”，要修根因。
- UI 任务要截图回归，不靠口头判断。

## 9. 模型选择要按阶段和任务路由

不要全程一把梭最贵模型。更稳的分工：

| 模型层级 | 用途 |
| --- | --- |
| 快速/低价模型 | 文件分类、短摘要、简单提取、批量初筛 |
| 日常主力模型 | 普通编码、文档、分析、多步骤工作流 |
| 高能力模型 | 架构设计、复杂调试、长文理解、关键 review |
| 计划专用高能力模型 | Plan Mode、迁移设计、风险识别 |

复杂任务可以“规划用高能力，执行用日常主力”。模型路由的目标是把深思考留给高价值节点，把重复体力活交给低成本模型。

## 10. 多 Agent 协作要靠边界，不靠热闹

Orchestrator-Workers 的价值是上下文隔离和并行，而不是同时开更多 Agent。建议三类 worker：

| 角色 | 权限 | 输出 |
| --- | --- | --- |
| Explorer | 只读 | 文件地图、调用链、风险点 |
| Implementer | 读写 + 验证命令 | 单一子任务的最小实现 |
| Reviewer / Verifier | 只读 diff / 测试结果 | 阻塞问题、风险和建议 |

会写代码的并行 worker 应使用独立 worktree，避免互踩文件。主线程只负责目标、派工、验收和合并。

## 11. 高风险迁移先搭桥，再搬家，最后拆桥

跨语言、跨框架、存档格式、后台接口和组件库迁移都不适合让 AI 一把改完。稳态流程：

1. Plan Mode 盘点依赖、非目标和验证门。
2. 建 adapter / shim，让旧新系统能并存。
3. 分批迁移，每批有测试、构建或截图验证。
4. 主路径稳定后再拆旧桥。
5. 每批打 checkpoint / 小提交，确保可回滚。

这套打法对 Unity 老存档、新配置字段、运营后台接口、数据工具服务化都适用。

## 12. Zero-Shot 应用生成要压成垂直切片

PRD + 截图不是许愿池。正确流程是：

1. 先写非目标：本轮不做什么。
2. Plan Mode 把 PRD 和截图翻译成页面、状态、数据模型、接口、验收。
3. 先搭最薄脚手架和验证门。
4. 只打通一条主用户路径。
5. 用截图、测试、build 验收。
6. 每次只扩一层复杂度。

从零生成应用的关键不是“第一天生成很多”，而是后续能稳定长出来。

## 13. AI 编程能力路线图：从会用到会带队

Claude Code / Codex 的学习路线可以按四层推进：

| 阶段 | 目标 | 关键能力 |
| --- | --- | --- |
| 入门 | 能用 CLI 完成简单脚本和问答 | 基础命令、上下文清理、单一职责提问 |
| 进阶 | 能完成中小功能和调试 | 入口文件、测试闭环、模型选择 |
| 高级 | 能主导跨文件复杂改动 | Spec 先行、多 Agent、CI / lint / test 自动化、Git review |
| 资深/专家 | 能设计半自动工程流水线 | TDD Agent、性能安全审查、迁移流水线、Zero-Shot 垂直切片、上下文工程 |

对个人游戏开发者，最优先补的不是花哨自动化，而是三件事：项目入口上下文、验证闭环、分批回滚。没有这三件，越高级的 Agent 流越容易把工程改乱。
