# 拆解：《妖之乡》

## 1. 一句话核心机制

玩家在东方幻想半开放世界里探索、收服和培养 300+ 妖灵，用阵容站位+技能天赋+符咒干预完成自走棋战斗，同时通过家园建筑、生产、繁育和任务线形成长线收集目标。

## 2. 核心循环

探索地图/接任务 -> 遇见野外妖灵/宗门/宝箱/资源 -> 捕捉或战斗 -> 获得妖灵、经验、材料、图鉴进度 -> 回村建设、繁育、制作、派工 -> 强化阵容 -> 解锁新区域/新任务/新 boss。

## 3. 玩法详解

### 公开资料确认

- Steam 官方 Q&A 将其定义为「生物收集、类开放世界、类自走棋战斗模式」RPG。
- 官方介绍确认：300 种妖灵，不同种族、属性、技能、天赋，可升级进化；存在异色、闪光、巨大体型等稀有变体。
- 战斗中妖灵自动作战，玩家侧重战前阵容、站位、天赋/技能理解，并在后方使用符咒治疗、增益、伤害、控制或封印捕捉。
- 家园/村庄部分包含解救工匠、解锁餐厅/繁育等建筑，以及耕种、挖矿、烹饪、制作符咒等生产。
- 正式版后更新加入了自定义岛屿、PVP/线上对决、免费 DLC 复古回合 RPG、更多妖灵和坐骑。

### 地图是否是大世界

判断：不是 AAA 式全无缝大开放世界，更像「大区域串联的半开放世界 / 类开放世界」。

依据：
- Steam 官方使用「类开放世界」，Gematsu 早期资料使用「expansive semi-open world」。
- 游戏配置极低，最低 2GB RAM、1GB 显存、8GB 存储，说明资源密度和实时加载压力远低于 3A 开放世界。
- 实际视觉是俯视/斜俯视 2D 角色+简化 3D 地形，外围看起来大，主要来自镜头视角、低密度地形、远景可视范围和场景重复资产。

### 加载方式推断

官方未披露具体加载实现。按 Unity、URP、低配要求和画面形态推断，较合理方案是：

1. 世界按区域/生态分场景：森林、麦田、雪原、水乡、山谷、宗门、村庄、岛屿、DLC 世界等。
2. 大区域内再按 chunk 或兴趣半径激活对象：近处怪物、NPC、采集物、草、花、碰撞、交互点启用；远处只保留静态地形和低成本装饰。
3. 资源用 Addressables/AssetBundle 或普通 Scene 分包异步加载，过门/传送/剧情点用淡入淡出遮蔽加载。
4. 植被用 Terrain Detail、Prefab Painter 或自研刷物工具批量刷，运行时依靠 GPU Instancing、LOD、距离裁剪。
5. 战斗大概率不切独立大场景，而是在局部战斗区域/战斗棋盘中锁定单位，降低状态同步和加载复杂度。

## 4. 程序系统拆分

P0 核心：
- 数据驱动框架：妖灵、技能、天赋、属性、元素克制、状态、道具、掉落、任务、地图生态、建筑配置。
- 探索地图：玩家移动、相机、坐骑、交互、传送点、区域加载、碰撞/NavMesh、寻路、地图标记、任务追踪。
- 野外生态：按区域刷怪、稀有变体、精英/邪魔、巡逻/追击/脱战、采集物和宝箱刷新。
- 自走棋战斗：布阵、单位 AI、索敌、移动、普攻、技能、弹道、AOE、BUFF/DEBUFF、控制、治疗、护盾、DOT、战斗结算。
- 符咒系统：战斗内施放、野外投射、冷却/消耗、捕捉判定、治疗/增益/控制/伤害/封印。
- 妖灵养成：捕捉、图鉴、队伍/仓库、经验等级、进化、天赋词条、研究等级、变体继承、装备/饰品/坐骑。
- 任务/剧情：主线、支线、NPC 对话、目标追踪、地图箭头、任务条件、剧情触发、奖励。
- UI/存档：背包、图鉴、队伍、属性面板、技能说明、地图、任务、商店、建筑、设置、Steam 云、成就。

P1 长线：
- 家园建设：建筑解锁、摆放/升级、工匠 NPC、生产队列、派工、餐厅/烹饪/挖矿/耕种/制作。
- 繁育系统：蛋、孵化、品质、天赋继承/随机、消耗资源、筛选和出售。
- 经济系统：材料、货币、制作配方、商店、委托、贸易路线、成长门槛。
- 钓鱼/小游戏：独立输入和结算，若非核心可后置。
- PVP/异步对战：阵容上传、对手筛选、好友挑战、战斗回放/服务端或本地校验。

P2 工具链：
- 妖灵/技能表编辑器、关卡刷怪表、生态区域编辑、任务编辑、对话编辑、地图标记校验、自动化数值检查。

## 5. 美术系统拆分

角色/妖灵：
- 玩家角色、NPC、宗门角色、工匠、商人、剧情角色。
- 妖灵 2D 资源：待机、移动、普攻、技能、受击、死亡/退场、进化形态、坐骑状态、异色/闪光/巨大体型表现。
- 头像、图鉴立绘、技能图标、状态图标、饰品/披风/坐骑外观。

3D 场景：
- 地形地貌：草地、麦田、雪地、河流、水乡、山谷、宗门、村庄、洞穴/深渊/特殊区域。
- 模块资产：房屋、桥、道路、栅栏、石头、树、灌木、花、草、农田、矿点、宝箱、神龛、传送点、交互物。
- 材质/Shader：低多边形或简化风格材质、水面、草/花摆动、闪光/稀有、技能特效。

关于草和花：
- 需要地编或场景美术刷，但不应手摆。
- 推荐流程：先用 Terrain Layer/地表贴图划生态区域，再用刷草工具按密度、坡度、高度、地表类型自动散布；关键路口、任务点、建筑周围手工修边。
- 技术要求：草花必须支持距离裁剪、GPU Instancing、批处理、碰撞关闭或极少碰撞，否则大地图会被植被拖垮。

## 6. 工期估算

前提：按 Unity PC/Steam、买断制、2D 角色+简化 3D 场景估算。

### 只做可验证 Demo

目标：1 个区域、20-30 只妖灵、基础探索、捕捉、自动战斗、3-5 个任务、1 个村庄建筑闭环。

- 1 程序 + 1 美术 + 1 策划兼职：3-5 个月。
- 2 程序 + 2 美术 + 1 策划：2-3 个月。
- 若只做概念视频/战斗切片：3-6 周可做，但不能验证长线。

### 做中等体量 EA

目标：4-6 个生态区域、80-120 只妖灵、完整战斗/捕捉/养成/任务/家园/繁育。

- 3-5 人稳定团队：8-14 个月。
- 1-2 人小队：14-24 个月，且内容量会明显缩水。

### 接近《妖之乡》完整体量

目标：300+ 妖灵、多生态大地图、完整主线、宗门挑战、家园生产、繁育、钓鱼、PVP、自定义岛屿、成就、多语言、长期 QA。

- 5-8 人团队：18-30 个月比较现实。
- 2-3 人团队：30-48 个月，最大风险不是程序框架，而是妖灵、美术、数值和 QA 内容债。

## 7. 技术注意点

1. 先做数据驱动。300 个妖灵和几十上百技能不能靠手写类，必须配置化、可批量校验。
2. 战斗要可复现。自走棋、技能触发、PVP/回放都需要 deterministic seed、战斗日志和调试面板。
3. 技能系统是最大坑。弹道、AOE、召唤、护盾、反伤、吸收、变形、投掷、打断、免疫、叠层、持续伤害会快速膨胀。
4. 2D 角色进 3D 场景要解决排序、阴影、落点、碰撞、朝向、Z-fighting、地形高度贴合。
5. 地图不要一开始追求真无缝。先做区域加载+传送点，把探索体验做大；等验证后再做 chunk streaming。
6. 草花刷量必须走工具和性能预算。每个生态要有密度上限、材质合批、距离裁剪和低端机测试。
7. 任务系统要早做。开放探索游戏最容易出现任务追踪错乱、传送点状态错、NPC 阶段错、目标箭头错。
8. 存档版本要从第一天设计。妖灵个体、天赋、任务、建筑、地图解锁、图鉴、背包、PVP 阵容都会进存档，后期改字段很痛。
9. 美术产能决定上限。300 个妖灵不是 300 张图，而是 300 套动作、技能表现、图鉴、图标、变体和 QA。

## 8. 跟用户已有项目的相邻度

- 跟《光与朽》：都可复用 Unity、战斗反馈、技能系统、Boss/精英设计经验，但《妖之乡》更偏内容型 RPG 和数值/收集长线，不是动作手感驱动。
- 跟《美妆叠叠乐》：相邻度低。它不是短局消除，而是长线收集+养成+探索。
- 对新方向的启发：如果要做微信小游戏，不建议照搬完整体量；可抽取「妖灵收集 + 自动战斗 + 家园派工」做轻量版，而不是先做大地图。

## 9. 可借鉴的 3 个点

1. 用 2D 妖灵节省角色建模成本，把美术重心放在可爱识别度、动作轮廓和技能特效。
2. 用自走棋战斗降低玩家操作压力，同时通过阵容、天赋、符咒保留策略和中局干预。
3. 用家园生产/繁育/图鉴把探索掉落转成长期目标，避免大地图只剩跑图。

## 10. 不该照抄的 1 个点

不要直接照抄「300+ 妖灵 + 大世界 + 家园 + PVP」的完整堆量。对小团队来说，最危险的是系统都做了 60%，但每个系统内容都不够厚，最后既没有短局爽感，也没有长线留存。
