# 系统设计与核心循环方法论

## 来源: `10_流水/Openclaw知识库文件/system_design.md` · 提取日期 2026-05-30

## 系统设计先看闭环，再看子系统数量

系统策划的核心不是堆功能名，而是让玩家的每一步操作都进入一个能自洽运转的闭环。

最基础的闭环：

```text
核心玩法获得资源 -> 资源进入经济系统 -> 养成提升能力 -> 挑战更高压力 -> 获得更多资源
```

这个闭环成立后，才讨论体力、活动、社交、排行榜、月卡或副本。否则子系统越多，越容易变成彼此抢注意力的菜单。

## 子系统要回答它服务哪一段循环

每个系统至少回答三个问题：

| 问题 | 判断标准 |
| --- | --- |
| 它给玩家什么目标 | 短期目标、中期解锁、长期毕业或社交竞争 |
| 它控制什么节奏 | 资源投放、游玩频率、内容消耗、付费触发 |
| 它如何回到核心玩法 | 提升能力、解锁新规则、改善失败体验或产生新挑战 |

常见系统分工：

| 系统 | 作用 | 风险 |
| --- | --- | --- |
| 养成系统 | 给长期目标和能力增长 | 只加战力会变成数值跑步机 |
| 经济系统 | 管理产出端和消耗端 | Faucet / Sink 失衡会通胀或卡死 |
| 活动系统 | 打破日常节奏，制造短期目标 | 活动奖励不能反向污染主循环 |
| 社交系统 | 排行榜、好友、公会、师徒等提高留存 | 小团队早期不应先做重社交 |
| 新手引导 | 分阶段暴露系统 | 一次性灌菜单会压垮首局 |

## 体力系统是节奏阀，不是单纯限制玩家

体力系统的价值不是“阻止白嫖”，而是控制短局游戏的回访节奏、广告补给和长期资源锚点。它适合已经有“再来一局”意愿的项目，不适合在核心乐趣还没被证明前先拿来卡玩家。

体力设计可用四层：

| 层级 | 设计要点 |
| --- | --- |
| 基础消耗 | 单局消耗清楚，扣除时机稳定，强退是否返还要提前写明 |
| 自然恢复 | 恢复速度决定每天回访节奏，例如 30 分钟 1 点 |
| 补给入口 | 签到、每日免费包、任务奖励提供轻量补充 |
| 商业入口 | 激励视频补体力，未来可接月卡、周卡或体力药水 |

体力可以允许广告、签到或补给溢出上限。溢出时 UI 显示 `当前 / 上限`，并暂停自然恢复倒计时。这样玩家会觉得奖励有价值，而不是被系统悄悄吞掉。

设计边界：

- 不要在首局或教学期过早卡体力。
- 体力不足弹窗要直说解决方案：等待、看广告、领取补给。
- 广告补体力要有每日上限，避免把用户疲劳当收入。
- 如果项目没有明确留存和广告意愿，不要为了“像商业游戏”硬加体力。
