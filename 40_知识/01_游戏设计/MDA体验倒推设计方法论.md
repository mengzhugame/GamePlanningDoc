# MDA 体验倒推设计方法论

## 来源: `10_流水/Openclaw知识库文件/game_design_mda_framework.md` · 提取日期 2026-05-26

## MDA 是体验倒推工具，不是术语分类

MDA 把游戏拆成三层：

| 层级 | 含义 | 设计问题 |
| --- | --- | --- |
| Mechanics | 规则、数值、输入、系统 | 玩家能做什么，系统如何响应 |
| Dynamics | 玩家与系统互动后出现的行为模式 | 玩家会如何选择、循环、博弈和失误 |
| Aesthetics | 玩家最终获得的体验 | 玩家为什么觉得紧张、爽、好奇或想研究 |

设计师常从 Mechanics 推到 Aesthetics，但玩家是从 Aesthetics 反向感知 Mechanics。玩家先感到爽、压迫、惊喜、困惑或无聊，再倒推“这个系统好不好”。所以做系统前要先写目标体验句，而不是先列功能表。

MDA 的常用体验类型包括：

| 体验 | 说明 |
| --- | --- |
| Sensation | 视听触觉爽感 |
| Fantasy | 身份幻想与角色代入 |
| Narrative | 故事推进与意义感 |
| Challenge | 挑战、克服和掌控 |
| Fellowship | 协作、社交和归属 |
| Discovery | 探索、发现和新奇 |
| Expression | 自我表达和风格选择 |
| Submission | 放松、消磨和仪式性 |

不要让一个小系统同时服务所有体验。每个功能先选一个主体验，再选一到两个辅助体验。

## 功能立项前先写“体验句”

MDA 的实用流程：

1. 写体验句：玩家应该感到什么。
2. 写动态句：玩家会产生什么行为模式。
3. 写机制句：系统需要提供什么规则和反馈。
4. 写验证句：用什么数据或观察判断它是否成立。

示例：

| 层级 | 《光与朽》示例 |
| --- | --- |
| Aesthetics | 玩家感到被怪潮压迫，但能靠激光清屏反杀 |
| Dynamics | 玩家在高密度敌人中寻找最佳旋转角度和 Build 成型机会 |
| Mechanics | 高密度刷怪、穿透/反射激光、蓄力清屏、波间三选一 |
| Verification | 记录清屏峰值、首个核心协同出现时间、Boss 失败原因和重开率 |

可落地的事件名示例：

```text
first_build_branch_chosen
first_core_synergy_online
boss_fail_reason
reroll_used
screen_clear_peak
daily_challenge_reentry
```

如果实际玩家行为和预期 Dynamics 不一致，不要急着加新功能，先检查 Mechanics 是否真的支撑目标体验。例如玩家说“无聊”，可能不是缺内容，而是安全角落策略太强；修正方向可能是加反蹲点敌人、路径变化或波次题型，而不是再加一个塔。

## MDA 卡片可以作为功能评审表

每个塔、敌人、Boss、奖励和局外成长节点，都可以用一张 MDA 卡评审：

| 问题 | 必答 |
| --- | --- |
| 主体验是什么 | 挑战、爽感、发现、表达等只能先选一个主项 |
| 预期动态是什么 | 玩家会因此做出什么选择或形成什么套路 |
| 机制如何支撑 | 规则、数值、反馈和 UI 是否对齐 |
| 失败信号是什么 | 玩家会如何表现出看不懂、没兴趣或被迫最优 |
| 验证数据是什么 | 埋点、录像、试玩问题或留存指标 |

功能如果无法回答“它服务哪种体验”，就先不要进入实现。小团队最容易浪费时间的不是少做系统，而是做出一堆彼此不解释、玩家也感知不到的系统。

## 拆解别人时也按 A-D-M 反推

做游戏拆解时，顺序应从玩家感受开始，而不是从系统列表开始。

```text
Aesthetics: 我玩的时候产生了什么情绪
Dynamics: 哪些局内行为不断制造这种情绪
Mechanics: 底层规则、数值和反馈如何支撑这些行为
```

示例判断：

| 玩家感受 | 动态问题 | 机制追问 |
| --- | --- | --- |
| 我想再来一局 | 上局留下了什么未完成假设 | 是否有失败复盘、随机分叉、低摩擦重开 |
| 我觉得自己很聪明 | 玩家做了什么选择并看见回报 | 是否有透明信息、协同组合、可控随机 |
| 我想分享这局 | 局内是否产生可转述事故 | 是否有反转、稀有奇观、排行榜或战报 |
| 我玩累了 | 操作或认知负担在哪一段堆积 | 是否缺少节奏停顿、自动化或目标压缩 |

拆解的最终目的不是“找到可抄功能”，而是提取体验生成机制。只有能回答“这条机制在我的项目里会生成什么体验、怎么验证”的设计点，才值得进入下一步原型。

## MDA 可以做成 AI 设计审问器

这份 MDA 重复稿的新增价值，是把 MDA 转成 AI 辅助策划提问模板。每当出现一个玩法设想、系统功能或玩家反馈时，AI 不应直接给方案，而应先拆三层：

```text
你想让玩家产生哪种 Aesthetic？
为了产生这种体验，玩家需要形成什么 Dynamics？
目前的 Mechanics 是否真的会引导出这些 Dynamics？
如果不会，应该改哪条规则、数值、反馈或输入？
用什么数据验证体验真的发生？
```

示例：

| 玩家反馈 | MDA 审问 |
| --- | --- |
| 不够爽 | 爽感来自清屏密度、命中反馈、质变节点还是成长节奏？ |
| 太累 | 是操作频率太高、休息窗口太少，还是单局目标太长？ |
| 看不懂 | 是机制没解释、动态没形成，还是 UI 没把结果反馈出来？ |
| 没策略 | 是选择没有代价，还是不同选择最后都导向同一动态？ |

AI 的职责不是把 MDA 术语复述一遍，而是把“玩家感受”翻译成可改的机制假设。每个建议最后都必须落到一个验证句：改完后观察什么数据或试玩反应。

## MDA 评审要看机制组合，而不是单点功能

单个 Mechanics 看起来合理，不代表组合后的 Dynamics 仍然健康。MDA 的实用价值之一，是在功能实现前追问“这些规则叠在一起后，玩家会不会发展出伤害体验的最优解”。

典型检查：

| 组合问题 | 可能后果 | 设计追问 |
| --- | --- | --- |
| 高奖励击杀 + 无保护复活 | 玩家蹲复活点，新人体验崩坏 | 是否需要无敌时间、出生点随机或收益衰减 |
| 高收益刷怪 + 固定安全角 | 玩家只守一个点，关卡变重复劳动 | 是否需要反蹲点敌人、路径变化或奖励递减 |
| 强 Build 协同 + 低重置成本 | 玩家只追单一套路，其他内容失效 | 是否需要反制题型、流派门槛或局内修正 |
| 失败惩罚重 + 信息不透明 | 玩家把失败归因于系统不公平 | 是否需要预警、回放、提示或轻复活 |

所以每个新机制不只要回答“它服务什么体验”，还要回答：

1. 它和现有机制组合后，会诱导玩家做什么。
2. 这个行为是我们想要的高光，还是会破坏首局、留存或公平感。
3. 如果玩家找到了最优解，是否仍然有趣、可读、可传播。
4. 哪个埋点或试玩观察能证明这个组合没有失控。

小团队做功能评审时，至少要给每个 P0 系统写一条“最坏动态假设”。这能防止团队把“机制已经实现”误当成“体验已经成立”。
