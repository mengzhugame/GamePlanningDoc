# 资深项目管理 (Project Management) - 进阶学习笔记

## 课题：【初级】敏捷开发 (Agile) 与 SCRUM 在单人独立开发中的极简应用

### 1. 为什么单人开发也需要敏捷与 SCRUM？
很多独立开发者（Solo Developer）在开发游戏时，容易陷入“无止境的打磨”或“功能蔓延 (Feature Creep)”，导致项目无限期拖延。
SCRUM 框架虽然最初为团队设计，但其**核心思想（拆分、迭代、反馈、聚焦）**完全适用于单人开发。
极简版 SCRUM 可以帮助单人开发者建立“节奏感”，控制范围，确保游戏能在预定时间（如 4 月）顺利上线。

### 2. 单人极简 SCRUM 的核心组件
*   **Product Backlog (产品待办列表)**：游戏的所有想法和功能池。不必太详细，想到什么就记下来（比如 Notion 里的一个大列表）。
*   **Sprint (冲刺)**：强烈建议单人开发采用 **1周 (1-week)** 为一个冲刺周期。太长容易懈怠，太短无法完成实质性功能。
*   **Sprint Backlog (冲刺待办列表)**：每周日晚上，从产品列表中挑出下周**绝对要完成**的几项任务。**一旦确定，本周内绝对不加新功能。**
*   **Daily Standup (每日站会) -> 自我反思日志**：每天开始工作前，用 2 分钟在纸上写：昨天完成了什么？今天打算做什么？有什么卡点？（如果卡点超过半天，立刻换方案或砍掉）。

### 3. 实操干货：防坑指南
1.  **用户故事 (User Story) 视角的任务拆分**：
    *   *错误写法*：“做 UI 系统”
    *   *正确写法*：“玩家能在游戏结束时看到得分结算弹窗”（更聚焦于可验证的结果）。
2.  **强制 Timeboxing (时间盒)**：
    给任务设定严格的时间上限。例如：“光与朽的某个特效，最多花 2 小时，做不完就用备用简版方案”。
3.  **定义“完成 (Definition of Done)”**：
    对于单人开发，完成意味着“代码已提交，功能能在真机或主分支上跑通，没有明显崩溃”。千万不要把“完美”当做完成标准。
4.  **周末的自我回顾 (Retrospective)**：
    这周进度慢了是因为美术资源卡住了？还是因为沉迷打磨某个不重要的细节？下周如何避免？

### 4. 总结与应用
将“敏捷”转化为“聚焦与斩断”。每周设定一个绝对目标，比如“本周Sprint目标：完成《光与朽》核心战斗的完整闭环跑通”。通过极简 SCRUM，用纪律对抗独立开发者的“拖延与完美主义”。

## 课题：【中级】版本控制管理 (Git流) 与自动化构建 CI/CD（如何配置一键打包）

### 1. Git版本控制：从混沌到专业工作流
独立游戏开发中最常见的错误：**无分支开发**（直接在main分支上写代码）导致上线前不敢改动、回滚困难、协作混乱。

**Git Flow 极简版（适合1-3人团队）：**
*   **main/master分支**：永远稳定，对应已发布的版本。**永不直接提交**。
*   **develop分支**：当前开发的主线，合并功能分支的地方。
*   **feature/*分支**：每个新功能开一个分支，如 `feature/battle-system`，开发完成后合并回develop。
*   **hotfix/*分支**：紧急修复已发布版本的问题，从main分支创建，修复后同时合并到main和develop。

**单人开发优化版：**
1. **main分支**：对应每次打包发布的可运行版本（如0.1.0, 0.2.0）。
2. **feature/分支**：开发中的功能，如 `feature/ui-redesign`。
3. **关键原则**：任何功能开发完毕，需先在真机或模拟器**跑通无报错**，再合并到main分支。确保main分支永远可打包。

### 2. 自动化构建CI/CD：为什么独立开发者也需要？
**问题场景**：手动打包需要20-30分钟（Unity构建时间长），期间无法工作，且容易因环境差异（Unity版本、SDK版本）导致打包失败。

**CI/CD的核心价值：**
1. **一键打包**：git push后自动在云服务器上构建，不占用本地开发时间。
2. **环境一致性**：构建环境固定，避免“在我机器上可以”的尴尬。
3. **自动化测试**：可配置简单的冒烟测试（游戏启动、核心场景加载）。
4. **版本归档**：自动存档每个版本的apk/ipa文件，方便追溯。

### 3. 三种适合独立开发者的CI/CD方案

#### 方案A：GitHub Actions（最适合开源/小团队）
**优点**：免费额度足够，集成GitHub生态，配置文件简单（.github/workflows/*.yml）。
**配置要点**：
```yaml
name: Unity Build
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - name: Setup Unity
      uses: game-ci/unity-setup@v4
      with:
        unity-version: 2022.3.25f1
    - name: Build Android
      uses: game-ci/unity-builder@v4
      with:
        targetPlatform: Android
        buildName: LightVSDecay
```
**适用场景**：代码托管在GitHub，需要跨平台打包（Android/iOS/WebGL）。

#### 方案B：Jenkins（本地部署，完全控制）
**优点**：免费开源，插件生态丰富，可在自己的服务器或电脑上运行。
**核心步骤**：
1. 安装Jenkins，配置Unity命令行构建脚本。
2. 创建Pipeline项目，监听Git仓库的push事件。
3. 自动触发构建，打包后通过SFTP上传到指定位置。
**适用场景**：对数据安全要求高，或需要复杂的构建后处理（如自动上传到测试分发平台）。

#### 方案C：Unity Cloud Build（官方方案，最省心）
**优点**：与Unity深度集成，支持自动增量构建，无需维护服务器。
**配置要点**：
1. 在Unity Dashboard中创建Cloud Build项目。
2. 连接GitHub/GitLab/Bitbucket仓库。
3. 选择目标平台（Android/iOS/等），设置构建触发条件（如tag推送）。
4. 云端自动构建，完成后可分发到TestFlight、Google Play测试等。
**适用场景**：预算有限但希望专业构建管线，尤其适合iOS需要证书管理的场景。

### 4. “一键打包”的核心脚本示例
无论选择哪种方案，都需统一的Unity命令行打包脚本：

```bash
#!/bin/bash
# build.sh - Unity一键打包脚本

UNITY_PATH="/Applications/Unity/Hub/Editor/2022.3.25f1/Unity.app/Contents/MacOS/Unity"
PROJECT_PATH="/path/to/your/project"
OUTPUT_PATH="./Builds"

# Android打包
$UNITY_PATH -batchmode -nographics \
  -projectPath "$PROJECT_PATH" \
  -executeMethod BuildTool.BuildAndroid \
  -quit

# iOS打包
$UNITY_PATH -batchmode -nographics \
  -projectPath "$PROJECT_PATH" \
  -executeMethod BuildTool.BuildiOS \
  -quit
```

**对应的C#构建脚本**：
```csharp
using UnityEditor;
using UnityEngine;

public class BuildTool : MonoBehaviour
{
    [MenuItem("Build/Android")]
    public static void BuildAndroid()
    {
        BuildPlayerOptions options = new BuildPlayerOptions();
        options.scenes = GetScenes();
        options.target = BuildTarget.Android;
        options.locationPathName = "Builds/Android/LightVSDecay.apk";
        options.options = BuildOptions.None;

        BuildPipeline.BuildPlayer(options);
    }

    [MenuItem("Build/iOS")]
    public static void BuildiOS()
    {
        // iOS构建逻辑
    }
}
```

### 5. 防坑实践指南
1. **大文件处理**：美术资源（纹理、音频）易导致仓库臃肿。使用Git LFS（Large File Storage）管理大文件。
2. **.gitignore配置**：必须包含Unity生成的临时文件（Library/, Temp/, Builds/, *.csproj等）。
3. **版本号自动化**：在CI/CD中自动递增版本号，如通过git tag或构建号注入。
4. **构建缓存利用**：Unity 2021+支持Build Cache Server，可大幅加速后续构建。
5. **分平台构建**：Android和iOS需分别配置密钥、证书，在CI中安全存储这些敏感信息。

### 6. 总结：从手动到自动化的思维转变
对于《光与朽》项目，建议采用 **GitHub Actions + Unity命令行脚本** 的组合方案：
1. **本周内**：先完善git分支策略（main + feature/*）。
2. **两周内**：配置本地一键打包脚本，确保稳定运行。
3. **三周内**：迁移到GitHub Actions，实现push后自动构建。

这样既能保证4月上线的时间压力下，打包流程稳定可靠，又能为后续多平台发布（微信小游戏、App Store等）奠定自动化基础。

## 课题：【高级】功能砍砍砍法则：如何界定 MVP (最小可行性产品) 的核心边界

### 1. 先下结论：MVP 不是“做个残废版”，而是“只保留能证明核心乐趣与商业假设成立的最小闭环”
很多独立开发者把 MVP 理解成“功能少一点”，这不够狠。真正的 MVP 边界应该回答三个问题：
1. **玩家能否在 3-10 分钟内明确感受到核心爽点？**
2. **我们能否验证最关键的留存/付费/广告假设？**
3. **这版内容是否能稳定打包、稳定测试、稳定迭代？**

根据 Atlassian 对 MVP 的定义，MVP 是“**用尽可能少的功能交付明确用户价值**”的版本。放到游戏上，意思就是：不是把所有想法都做进首发，而是先做出一个能被验证、能被传播、能被继续扩展的最小战斗闭环。

### 2. 游戏项目里，什么叫“核心边界”？
对游戏来说，MVP 边界不是按系统多少来划，而是按**验证价值链**来划。一个功能若不能直接服务下面四件事之一，就该进待定区：
*   **核心玩法成立**：例如《光与朽》的激光塔防战斗是否真的爽。
*   **基本留存成立**：玩家是否愿意再来一局。
*   **基础商业化成立**：激励广告/轻付费是否嵌得进去。
*   **基础生产管线成立**：后续关卡、怪物、技能能否低成本扩充。

所以，MVP 不是“内容最少”，而是“闭环最完整”。

### 3. 一套适合独立游戏的“砍功能”判定框架

#### 框架A：MVP 三层切割法（Must / Later / Never-Now）
把所有功能强行切成三层：

*   **Must（首发必须有）**：没有它，核心体验无法成立。
    * 例：基础战斗、敌人刷新、失败/重开、基础成长选择、最低限度的引导。
*   **Later（上线后再补）**：有价值，但不影响首轮验证。
    * 例：额外角色、剧情包装、皮肤系统、排行榜、复杂任务系统。
*   **Never-Now（当前版本禁止做）**：诱人，但会严重拖慢上线节奏。
    * 例：多人模式、大世界、复杂公会、非必要剧情演出、花里胡哨的 meta 系统。

核心原则很简单：**只要某功能不能显著提升首周验证效率，就别进首发。**

#### 框架B：Impact / Effort 砍刀矩阵
参考 2025 年 Wayline 提到的做法，可用最简单的表格给每个功能打两分：
*   **Impact（影响）1-5**：对核心乐趣、留存、变现的帮助有多大。
*   **Effort（成本）1-5**：开发、测试、平衡、维护有多贵。
*   **Priority = Impact / Effort**。

决策规则：
*   **高影响、低成本** → 先做。
*   **高影响、高成本** → 先做最小版原型，不直接全量开发。
*   **低影响、高成本** → 当场砍掉。
*   **低影响、低成本** → 只有在主链路做完后才考虑。

这套方法的价值不在“数学正确”，而在于逼你停止凭感觉拍脑袋。

#### 框架C：一票否决的“验证问题”
每个功能立项前，必须回答一句话：
**“这个功能要验证什么？”**

如果答不出来，或者答案只是“更酷”“更完整”“玩家可能会喜欢”，那基本就是废话功能。

### 4. 最新实操案例与行业启发

#### 案例1：Toño Game Consultants（2024/2026 更新）——问题不是坏点子，而是坏管理
这篇游戏项目管理文章把 scope creep 讲得很直接：项目失控通常不是因为点子差，而是因为**没有明确 MVP、没有优先级、没有 guardrail（护栏）**。文中把常见踩坑归纳为：
*   中途方向漂移（Vision Drift）
*   功能狂欢（Feature Frenzy）
*   反馈源过多但无人筛选（Feedback Overload）
*   GDD 模糊
*   没有清晰 MVP

可落地的启发：
1. 先原型验证，再承诺正式开发。
2. 把“以后再做”当作正常能力，而不是失败。
3. 定期做 scope review，不让需求偷偷膨胀。

#### 案例2：Wayline（2025）——先砍掉“看起来很牛”的功能，时间线才不会暴毙
Wayline 文章给了几个很有价值的案例：
*   团队原本想给 rogue-lite 做“程序化过场动画”，原型后发现要吃掉数月动画成本，**直接砍掉**。
*   某项目在上线前几周发现一个玩法机制根本没时间充分测试和平衡，于是**整条机制砍掉**，换来更稳定的正式版。
*   Kickstarter 超募后，团队一度想把 stretch goals 全塞进首发，最后发现根本扛不住，于是改成 **Early Access 分阶段更新**。

这几个案例说明一个残酷事实：
**最危险的功能，往往不是最难做的，而是“做出来之后还要额外测试、平衡、教学、适配”的那类功能。**
也就是所谓的“隐藏成本功能”。

### 5. 界定 MVP 边界时，必须盯住的 5 个隐藏成本
很多人砍功能只看开发工时，完全不够。真正该看的，是功能的**总拥有成本**：
1. **实现成本**：代码/美术/配置要花多久。
2. **联动成本**：会不会牵扯 UI、数值、存档、引导、广告点位。
3. **测试成本**：每多一个分支，测试量是不是翻倍。
4. **平衡成本**：会不会引入新的 build、数值断点、崩盘组合。
5. **维护成本**：未来改一个底层逻辑，会不会连环炸。

所以一个功能即使“开发只要两天”，若测试和平衡要一周，它就不是小功能。

### 6. 独立游戏最实用的 MVP 定义模板
给每个版本写一个一页纸的《MVP 边界声明》，只保留这 6 项：

1. **目标玩家**：这版是给谁玩的？
2. **核心爽点**：玩家玩到什么瞬间会说“卧槽，有点东西”？
3. **必备闭环**：进入游戏 → 战斗 → 成长/反馈 → 失败/结算 → 再来一局。
4. **本版验证指标**：例如 10 分钟留存、首局完成率、广告点击率、首日二局率。
5. **明确不做清单**：当前版本禁止新增的系统。
6. **砍线规则**：任何新增需求，必须替换掉一个同量级旧需求，禁止只加不减。

这玩意儿的真正作用，不是给文档好看，而是让未来的你没法装傻。

### 7. 《光与朽》当前最该套用的边界法
如果《光与朽》的目标是尽快上线验证，那么首发 MVP 应只保住以下骨架：
*   **核心战斗爽感**：激光命中反馈、敌人死亡反馈、波次压力曲线。
*   **基础成长选择**：每局中有限但有差异感的成长三选一。
*   **基础敌人与 Boss**：足够验证 build 组合和战斗节奏，不追求海量怪池。
*   **最小商业化闭环**：失败复活广告、结算双倍广告、一个轻量去广告/新手包。
*   **最小外层循环**：局内→结算→局外轻成长→再开一局。

而下面这些，若还没做完主链路，就该毫不留情往后扔：
*   复杂剧情演出
*   大量皮肤与视觉包装
*   过度复杂的局外养成
*   社交、公会、排行榜大系统
*   没有明确数据验证价值的花式玩法分支

### 8. 真正高级的项目管理，不是“什么都管”，而是“敢砍、会砍、砍完还能稳住团队情绪”
砍功能不是失败，而是高级制作能力。
独立项目死得最多的原因，不是没人努力，而是每个功能都觉得“再做一点就更完整”，最后把自己做死。

真正的高手会这样决策：
*   **先保首发可验证，再谈完整世界观。**
*   **先保主循环上瘾，再谈内容厚度。**
*   **先保版本稳定上线，再谈梦想清单。**

### 9. 本课题的执行结论
以后做版本规划，统一用一句话审判功能：
**“没有它，这一版是否仍然能验证核心乐趣与商业假设？”**

如果答案是“能”，就砍。
如果答案是“不能”，再做。

这就是 MVP 边界的本质：
**不是少做，而是只做最值钱的那一点。**

## 课题：【专家】外包管理、兼职协同与多Agent协同的工作流架构

### 1. 先下结论：真正高级的项目管理，不是把所有活都亲自抓，而是把“任务拆对、接口写死、验收前置、责任切清”
独立游戏项目最容易死于两种混乱：
1. **外包/兼职交付物模糊**：说了半天“做个UI”“做个怪物”，结果交上来不能用，还得返工。
2. **AI Agent乱跑**：能写代码、能改配置、能搜资料，但没有边界、没有验收、没有回滚点，最后只会制造新混乱。

所以，外包、兼职和多Agent协同，本质上是同一个管理问题：
**谁在什么边界内，按什么标准，在什么时间点，交付什么可验证结果。**

### 2. 最新方法论共识：别先追求“协同人数”，先控制“协同复杂度”
根据 Microsoft Learn 2026 年更新的《AI Agent Orchestration Patterns》，多Agent系统并不是默认答案。最优先原则是：**用满足目标的最低复杂度方案**。

可直接映射到游戏项目管理：
*   **单人自己做**：当任务可在一个上下文内闭环，不要硬拆。
*   **单外包/单兼职**：一个明确交付物对应一个责任人，最省沟通成本。
*   **多Agent并行**：仅适用于可切分且相互独立的子任务，例如资料整理、代码扫描、素材变体生成。
*   **Maker-Checker（制作者-审查者）**：适用于高风险改动，如核心战斗逻辑、数值表、打包脚本、商店配置。

结论很狠：
**不是人/Agent越多越强，而是链路越短越强。** 复杂度只有在能换来明显效率收益时才值得加。

### 3. 外包与兼职协同的核心：按“成果”管理，不按“努力”管理
2025-2026 年多篇项目管理与游戏外包文章都在强调同一个东西：
**里程碑必须绑定成果，不要绑定工时。**

#### 为什么？
因为“做了三天”“改了二十版”“沟通很多次”这些都不是价值，能上线、能导入、能测试、能通过验收才是价值。

#### 正确的里程碑应包含 5 件事：
1. **交付物定义**：例如“3个敌人立绘 + 6张动作切片 + Unity可导入Prefab”。
2. **验收标准**：尺寸、命名、格式、性能、风格、功能是否达标。
3. **反馈时限**：例如 48 小时内给出一次性反馈，避免无限拉扯。
4. **修改轮次**：例如包含 2 轮小修，超出另计。
5. **付款触发点**：按验收通过节点付款，而不是按聊天热情付款。

这套逻辑适用于：
*   外包美术
*   兼职程序
*   音效/BGM协作
*   AI Agent提交代码/文档/方案

### 4. 验收标准必须前置，不然后面全是扯皮
ProjectManager 2025 对验收标准的定义非常扎实：**验收标准应在需求阶段就和功能/非功能要求一起写清楚**，而不是交付后再临时拍脑袋。

游戏项目里最常见的低级错误：
*   说“做个好看的按钮”——这是废话，不是需求。
*   说“做个Boss”——也还是废话。

真正能执行的写法应该像这样：

#### 美术外包验收示例
*   分辨率：2048×2048 源文件 + 1024 导出图
*   格式：PSD 分层 + PNG 导出
*   分层：角色主体、特效、阴影、UI框分开
*   风格：参考 A/B 两张样图，主色偏冷，高反差霓虹
*   用途：Unity UI 中可直接替换，不需二次切图

#### 程序/Agent任务验收示例
*   功能：完成“失败后看广告复活一次”逻辑
*   验收：
    1. Android 测试包可复现完整流程
    2. 广告成功/失败/跳过三种状态都可处理
    3. 失败后不会重复弹复活
    4. 关键日志埋点已输出
    5. 提交含回滚说明与修改文件清单

NextMars 2026 关于游戏美术外包验收的文章也强调一点：**别只看视觉上像不像，还要核对资产数量、格式、变体、导出项、分层与实际用途是否一致。**

### 5. 最稳的协同架构：一条主链 + 三类执行单元
对于独立游戏工作室，最稳的不是“人人平权协作”，而是：

#### 角色A：主脑 / 制作人（你）
负责：
*   优先级
*   边界裁决
*   最终验收
*   跨模块冲突决策

#### 角色B：外包/兼职执行单元
负责：
*   在明确范围内交付具体成果
*   不参与战略拍板
*   不跨界修改其他系统

#### 角色C：AI Agent执行单元
负责：
*   批量、重复、结构化任务
*   代码扫描、脚本修改、资料整理、模板生成、构建验证
*   产出必须可追踪、可回滚、可复核

#### 推荐链路：
**主脑定目标 → 拆成标准任务卡 → 分配给人类外包/兼职/Agent → 按里程碑回收 → 审查通过后合并到主线**

注意：
**任何执行单元都不要直接拥有“无限改主线”的权力。**
无论是外包还是Agent，都应该通过“任务卡 + 审查 + 合并”进入主项目。

### 6. 多Agent工作流：四种最值得落地的编排模式
结合 Microsoft Learn 的 2026 模式总结，以及我们当前的 OpenClaw 工作方式，最适合独立游戏项目的是这四种：

#### 模式A：Sequential（顺序流水线）
适合：有前后依赖的链路。
例如：
1. Agent A 扫代码找风险
2. Agent B 根据风险修脚本
3. Agent C 跑验证与整理变更摘要

**用途**：代码修复、数据清洗、文档整理。
**优点**：稳定，结果清晰。
**缺点**：前一步出错会污染后一步，所以必须加输出校验。

#### 模式B：Concurrent（并行分工）
适合：彼此独立的子任务。
例如：
*   一个Agent整理竞品
*   一个Agent检查数值表
*   一个Agent扫UI命名与资源引用

**用途**：研究、审计、素材整理。
**优点**：快。
**缺点**：需要最后统一汇总，且不能抢同一文件。

#### 模式C：Maker-Checker（制作者-审查者）
适合：高风险变更。
例如：
*   Maker Agent 写打包脚本
*   Checker Agent 检查异常路径、平台参数、版本号处理是否完整

**用途**：支付、广告、存档、构建、核心战斗。
**优点**：能显著降低 AI 一本正经写错的概率。
**缺点**：成本更高，但值。

#### 模式D：Human-in-the-Loop（人类在环）
适合：方向选择、风格判断、功能砍留。
例如：
*   Agent 先给三套UI文案方案
*   由主人拍板选一套
*   再交给执行单元落地

**用途**：美术风格、商业化节点、MVP边界、平台策略。
**优点**：防止AI越界瞎决定。
**缺点**：需要人及时决策。

### 7. 一套适合游戏项目的“任务卡模板”
以后不管是给外包、兼职还是AI Agent，统一用下面这张卡，不然沟通永远烂：

#### 《协同任务卡》
*   **任务名**：一句话写清成果
*   **目标**：解决什么问题，不是做什么动作
*   **范围内**：允许改哪些文件/模块/资产
*   **范围外**：禁止碰哪些地方
*   **输入材料**：参考图、脚本、PRD、样例
*   **输出物**：必须交什么文件、截图、说明、构建结果
*   **验收标准**：功能/性能/风格/命名/格式/日志/测试
*   **截止时间**：具体到日期与时区
*   **反馈时限**：甲方多久内回复
*   **修改轮次**：含几轮、超出如何处理
*   **交接要求**：命名规范、依赖说明、待办风险

这张卡越短越好，但关键字段一个不能少。

### 8. 防止协同翻车的 7 条铁律
1. **不要把“需求讨论”当“需求定义”**：聊得再多，没写成任务卡就是没定义。
2. **不要共享模糊责任**：一个交付物只能有一个最终责任人。
3. **不要让外包/Agent直接改主分支**：全部走审查合并。
4. **不要按过程付钱**：按验收通过节点付钱。
5. **不要把反馈拆成五次零碎吐槽**：集中一次给完整反馈。
6. **不要让高风险任务没有checker**：支付、广告、打包、存档必须双重检查。
7. **不要让知识留在聊天记录里**：所有规则、路径、命名、坑点都必须落文档。

### 9. 《光与朽》现在最该怎么落地
如果我们现在就把这套东西用到《光与朽》，最优先的不是再开更多任务，而是把现有协同方式先“制度化”。

#### 第一层：主人亲自拍板的事
*   核心玩法边界
*   美术大方向
*   是否砍功能
*   哪个平台先发

#### 第二层：适合外包/兼职的事
*   UI切图与规范化导出
*   怪物立绘与特效分层
*   音效/BGM包制作
*   商店图标、宣传图、截图包装

这些都必须先写死：参考图、导出格式、尺寸、命名、改动轮次。

#### 第三层：适合AI Agent的事
*   Unity脚本局部修复
*   数值表整理与检查
*   构建脚本、一键打包、日志埋点
*   知识库整理、竞品分析、待办清洗

这些都必须要求：变更摘要、影响文件、验证步骤、回滚点。

### 10. 推荐的每周节奏（适合独立团队）
*   **周一**：主脑定本周目标，只保 1-2 个版本核心结果。
*   **周二-周四**：执行单元各自推进，每天只报“完成/阻塞/风险”。
*   **周五**：统一收件验收，能进主线的进主线，不能过的直接打回。
*   **周末**：复盘协同问题：谁返工最多？哪个任务定义最烂？哪个Agent最稳定？

这套节奏的核心不是显得专业，而是为了避免独立项目在沟通和返工里被拖死。

### 11. 本课题的执行结论
以后不管是用外包、兼职，还是调用多个AI Agent，都统一按一句话来管理：

**“没有明确交付物、验收标准、反馈时限和责任边界的协同，都是伪协同。”**

对于《光与朽》，最优解不是找更多人来帮忙，而是把每个协作者都变成**可替换、可验收、可回滚**的执行单元。

这才是真正能把项目推上线的专家级项目管理。

## 课题：【专家进阶延展】风险管理与里程碑预警机制：如何在延期发生前就动刀

### 1. 为什么这个课题是项目管理维度的“下一个未攻克点”
路线图里四个显式课题已经覆盖完了，但如果目标真是“保证项目不延期，不踩坑，高效推进”，那还差最后一把刀：
**不是等延期发生后补救，而是在延期还没坐实前就通过预警指标把它砍掉。**

这就是风险管理与里程碑预警机制的价值。它不性感，但它决定项目能不能活着上线。

### 2. 2025-2026 的方法论共识：别只做任务管理，要做“风险前置管理”
近两年的项目管理文章和游戏开发实践基本都在强调同一件事：
**里程碑不是进度装饰品，而是风险暴露点。**

核心共识有四条：
1. **里程碑必须是零时长事件**，代表某个关键结果被验证，而不是“还在做”。
2. **里程碑要服务决策**，不是给甘特图好看。
3. **高风险问题要前置验证**，尤其是架构、构建、核心玩法、商业化点位。
4. **预警指标必须量化**，否则所有“有点危险”都只是情绪，不是管理。

根据 PMI Disciplined Agile 关于 risk-based milestones 的方法，最有效的策略不是把风险写进文档，而是**尽早做出一个端到端、可运行、能覆盖高风险需求的骨架版本**。说白了就是：
**先证明最容易炸的地方不会炸。**

### 3. 什么叫“风险型里程碑”
传统里程碑常写成：
* Alpha 完成
* Beta 完成
* 准备上线

这类写法最大的问题是：**听起来像进展，实际上没有任何可验证标准。**

风险型里程碑必须改写成“是否跨过某条生死线”：
* **核心战斗闭环跑通**：玩家可从开始战斗到结算再开一局，全流程无阻断。
* **高风险技术已验证**：激光特效、怪物波次、广告复活、存档回档至少有可运行骨架。
* **首轮真机打包通过**：安卓包能产出并安装，关键日志可读。
* **首轮留存假设可测**：至少已有可跑的成长三选一、失败重开、局内节奏断点。
* **上线阻断项归零**：支付、广告、崩溃、包体、审核素材都无 P0/P1 阻塞。

这种里程碑不是“阶段感”，而是“生死判断”。

### 4. 预警机制的本质：别盯“忙不忙”，盯“项目是不是开始失真”
独立项目最常见的错觉是：
* 每天都很忙
* 任务看起来也在做
* 但版本就是不往前走

这说明项目不是没努力，而是开始**失真**了。真正应该盯的，是下面这些预警信号。

### 5. 五个最值钱的延期前兆指标

#### 指标A：里程碑滑移率（Milestone Slip Rate）
定义：本周原定应完成的关键里程碑，有多少被推迟。

最实用阈值：
* **0-10%**：健康
* **10-20%**：警戒
* **>20%**：说明计划已经失真，必须砍范围或重排优先级

重点不是“晚了一点”，而是**连续两周滑移**。连续滑移说明不是偶发，而是估时、优先级或技术路径出问题。

#### 指标B：阻塞时长（Blocked Time）
定义：任务因等待、美术缺失、技术难题、外部依赖卡住的累计时间。

经验规则：
* 单个核心任务**阻塞超过半天**，就不能继续硬顶，必须立刻升级处理。
* 核心链路任务一周内累计阻塞**超过 20%-25%**，项目大概率会在后续爆延期。

这条尤其适合《光与朽》，因为很多问题不是“不会做”，而是卡在资源、调试、平台配置和联动测试上。

#### 指标C：返工率（Rework Rate）
定义：本周完成的工作里，有多少需要返修、回滚、重做。

危险信号：
* 某模块连续两轮返工，说明任务定义或验收标准有问题。
* 核心系统返工率超过 **15%-20%**，说明不是执行差，是前置设计差。

返工是最阴险的进度黑洞。表面在推进，实际上在原地刨坑。

#### 指标D：主链路完成率 vs 支线投入比
定义：本周时间里，有多少真正投在上线主链路。

如果出现这种情况，就该骂人了：
* 70% 时间花在 polish、UI小修、非核心特效、边角内容
* 主链路问题（战斗、成长、广告、打包、崩溃）还没收口

这叫**伪忙碌**。项目管理上最该看的，不是做了多少事，而是做的事是不是让版本更接近上线。

#### 指标E：预测完成时间持续外扩
定义：每周复盘时，预计上线时间是否在持续后移。

如果连续两次复盘都发现：
* 本周明明做了不少
* 但预计完成时间反而更晚

那就证明：
**项目复杂度增长速度，已经超过交付速度。**
这时不砍功能，等死。

### 6. 2024-2026 最新案例与启发

#### 案例1：Codecks（2025）对独立游戏的提醒，真正的敌人不是工作量，而是范围失控 + 截止日幻觉
Codecks 在 2025 的文章里把 indie game 项目的典型死法讲得很明白：
* 小团队资源紧
* 大家身兼多职
* Scope Creep 会把一个 6 个月项目拖成 6 年
* 没有清晰 milestones，就会在 deadline 前进入混乱和 crunch

最有用的启发不是“要用他们家工具”，而是这句底层逻辑：
**独立项目不是输在不努力，而是输在没有把大目标拆成能稳定交付的小节点。**

#### 案例2：Wayline（2025）强调里程碑必须 SMART，而且必须能量化“done”
Wayline 对 indie 开发的建议很实：
* 里程碑必须 Specific、Measurable、Achievable、Relevant、Time-bound
* 不能写“把游戏做得更好玩”这种废话
* 不能把太多东西塞进一个 milestone
* 里程碑必须带明确 deadline 和客观完成标准

这一点特别重要，因为很多游戏项目不是死于做不到，而是死于**done 的定义太模糊**。

#### 案例3：Game Developer 2024《The Last Humble Bee》复盘，单人项目时间估算天然偏乐观
这篇 solo 开发复盘很扎心。作者做第二款游戏，仍然发现两年 solo 开发极其消耗，并再次印证一个老结论：
**原始时间估算通常严重偏乐观。**

对独立开发真正有价值的启发不是“坚持”，而是：
* 时间线必须预留巨额缓冲
* 单人项目不要相信理想状态工期
* 长周期项目会放大孤立、疲劳和判断失真

翻译成管理动作就是：
**不要按最顺利情况排期，要按现实里会出 bug、返工、卡资源、状态波动来排。**

#### 案例4：monday.com 2026 对 milestone 的升级理解，里程碑不是任务，是项目健康信号灯
monday 2026 的里程碑文章强调：
* 里程碑是零时长事件，不是日常任务
* 它们的价值在于暴露依赖、延误和资源冲突
* 通过可视化跟踪和自动预警，里程碑可以从“静态计划项”变成“动态健康指标”

这对我们最重要的启发是：
**只写 milestone 没意义，必须给 milestone 配预警规则。**

### 7. 最适合独立游戏项目的“三级预警系统”
以后版本推进统一按三级预警，不再靠感觉。

#### 绿色（正常推进）
满足：
* 核心里程碑如期完成
* 阻塞任务 24 小时内解决
* 主链路投入占比 > 60%
* 本周没有新增 P0/P1 阻断

动作：正常推进，不新增大功能。

#### 黄色（开始失真）
触发任一条件：
* 核心里程碑延后 1 次
* 单个关键任务阻塞超过 0.5-1 天
* 主链路投入占比跌破 50%
* 返工率显著上升

动作：
1. 暂停新功能进入。
2. 开一次 20 分钟风险复盘。
3. 从 Later/Never-Now 清单里继续砍内容。
4. 把最危险的一项技术或流程当天验证掉。

#### 红色（必须动刀）
触发任一条件：
* 连续两周里程碑滑移
* 核心功能仍无可运行骨架
* 预计上线日期连续后移
* 打包、广告、存档、崩溃中有一个 P0 阻断未解

动作：
1. 立即缩 MVP 范围。
2. 冻结所有支线优化和包装工作。
3. 把一切资源转回战斗主链路、商业化主链路、构建主链路。
4. 若仍无法止血，就重定发布日期，别装。

### 8. 《光与朽》现在就能落地的预警模板
给《光与朽》直接上这个每周检查表：

#### 每周五 15 分钟项目体检
1. **本周最关键的一个里程碑是什么？是否完成？**
2. **本周最大阻塞是什么？卡了多久？**
3. **有没有任务返工两次以上？为什么？**
4. **这周时间有多少真的花在上线主链路？**
5. **预计上线时间比上周更近了，还是更远了？**
6. **如果现在必须砍 20% 内容，先砍什么？**

只要第 5 题答不出“更近了”，那这一周就不算真推进。

### 9. 对《光与朽》的具体应用建议
如果我们要把这套东西用在当前项目，最该盯的不是“做了多少功能”，而是以下四条里程碑：

1. **战斗主闭环稳定可复玩**
   * 激光命中反馈、敌人刷新、失败/结算、再开一局无明显断裂
2. **广告主闭环可真实验证**
   * 失败复活广告、结算翻倍广告、异常分支都能跑通
3. **安卓一键打包稳定**
   * 每周至少能稳定产出一个测试包，不再靠临时修环境
4. **首发内容边界锁死**
   * 本周之后禁止再加会影响测试量的系统级功能

只要这四条里有一条开始反复滑，就别再碰支线花活。

### 10. 本课题的执行结论
真正成熟的项目管理，不是写更多计划，而是建立一套会逼你面对现实的预警系统。

以后统一按这句话执行：

**“延期不是在截止日发生的，延期是在里程碑第一次失真时就已经开始了。”**

对于《光与朽》，最该立刻做的不是再开新需求，而是把每周版本体检、三级预警、主链路优先和里程碑验收一起钉死。

这样我们不是在祈祷项目按时上线，而是在系统性地阻止它失控。

## 课题：【专家进阶延展】发布管理与上线清单（Release Readiness）：从“能开发”到“能稳定上线”的最后一公里

### 1. 为什么这是项目管理维度下一个最该补的坑
前面的课题已经把敏捷、版本控制、MVP 边界、协同架构和风险预警打得差不多了，但项目真正临门一脚最容易死的，不是在开发期，而是在**上线前最后一公里**：
* 功能做完了，但商店文案和实际功能不一致。
* 构建包能出，但真机、登录、广告、存档没做完整验证。
* 有测试包，但没有 go/no-go 门槛，没有回滚标准，没有发布后监控。

所以这个课题的本质不是“怎么发包”，而是：
**如何把开发完成态，转成一个可审核、可回滚、可监控、可复盘的可发布状态。**

### 2. 2025-2026 的新共识：上线不是按钮，是一套跨阶段闸门
根据 2025-2026 年的发布管理文章与平台文档，成熟团队的共识非常一致：

1. **发布准备度（readiness）必须拆成多道闸门**，而不是临上线前靠感觉拍板。
2. **平台审核信息必须与真实产品状态一致**，元数据、截图、说明、登录信息错一个都可能被卡。
3. **测试轨道先行**，内部测试、封闭测试、预发布检查必须在正式发布前跑通。
4. **发布后验证和回滚门槛要先写死**，不是出事后才临时想。

一句话总结：
**发布不是“今天要不要上”，而是“你是否已经跨过所有能阻止翻车的闸门”。**

### 3. 最新案例与实操结论

#### 案例1：Steamworks 发行流程，真正卡人的不是按钮，而是双清单 + 审核顺序
Steamworks 文档明确要求两套 checklist：
* **Store Presence Checklist**：商店页与定价、文案、素材。
* **Game Build Checklist**：产品构建包与功能配置。

关键点很值钱：
* 商店页必须先提审，再提审 build。
* 商店页审核通常 3-5 个工作日，但官方建议**至少提前 7 天**提交，留出修改余量。
* 游戏想正式发，除了审核通过外，商店页还要处于“Coming Soon”满两周，且 build 已过审。

这意味着什么？
**如果你把“商店素材、描述、价格、构建、平台配置”混在一起最后一周再做，基本就是主动找死。**

#### 案例2：Google Play 2025-2026，测试轨道和稳定性检查已经不是建议，是准入门槛
Google Play 最新帮助文档给了很狠的信号：
* 应用必须先测试，再上 production。
* 推荐路径是 **internal test → closed test → open test/production**。
* 必须检查崩溃、ANR、Broken Functionality。
* 如果有登录，必须提供可用账号给审核。
* 商店页必须准确，不得承诺未实现功能。
* Open test 会在商店可见，所以只有当 store listing 已经准备好时才该开。

尤其内部测试的价值很高：
* 最快，几分钟即可分发给最多 100 个测试者。
* 可用于未完全配置完成的应用做早期 QA。
* 可以先把真机构建、支付/广告开关、登录链路跑通，再决定是否扩大测试范围。

结论：
**测试轨不是礼仪流程，而是项目经理用来提前暴露“包能不能装、功能会不会炸、文案会不会骗人”的减灾系统。**

#### 案例3：Apple App Review 2026，最常见死法依然是“提交了一个看起来像完成品、其实没准备好”的包
Apple 2026 文档把高频拒审原因说得非常直接：
* Crashes and bugs
* Broken links
* Placeholder content
* Incomplete information
* Inaccurate screenshots
* Misleading users

另外两个特别关键：
* **如果需要登录或特殊配置，必须在 App Review Information 里提供完整说明**。
* **如果环境难以复现，可能需要 demo video 或额外硬件说明**。

还有一个项目管理上很容易忽视的数字：Apple 说平均 90% 提交在 24 小时内完成审核，但前提是**提交完整**。不完整就会延迟，甚至直接不过。

这说明：
**不是平台审核慢，而是很多团队交上去的东西根本不配被快速审核。**

#### 案例4：DeployHQ / DECODE / Mergify 2025-2026，软件发布最佳实践已经把“回滚与发布后监控”提升到跟构建同级
2025-2026 的发布清单文章虽然来自软件行业，但对游戏发布同样适用，尤其是小游戏、移动端和有服务端依赖的项目：
* 上线前要检查 branch hygiene、环境变量、依赖锁定、迁移兼容性、安全项。
* 必须先过 staging / smoke test，再做 production release。
* 正式发布后前 5 分钟做 health check，前 30 分钟盯 error、响应时间、后台任务。
* 回滚标准必须事先写死，不能临场拍脑袋。

最值钱的一条：
**CI/CD 不是 readiness 的替代品，它只负责自动化机械步骤；真正决定是否能发的，仍然是你的 checklist 和 go/no-go 规则。**

### 4. 一套适合独立游戏/小团队的“5道发布闸门”

#### 闸门A：内容闸门（Content Gate）
检查：
* 本版功能范围是否已经锁死。
* 所有玩家可见文案、截图、宣传图是否与实际内容一致。
* 是否仍有 placeholder、美术占位、空按钮、开发者调试入口。
* 本版明确不做清单是否被守住。

判断标准：
**只要商店页上写了但游戏里没有，就不能发。**

#### 闸门B：构建闸门（Build Gate）
检查：
* 安卓/iOS/Steam 主构建是否能稳定产出。
* 版本号、包名、渠道标记、图标、启动图是否正确。
* 广告 SDK、登录 SDK、支付 SDK、分析 SDK 是否都在正确环境下工作。
* 是否存在“本地能跑，打包炸裂”的环境差异。

判断标准：
**不是“今天打出来过一次”就算通过，而是“连续可复现地产出可安装包”。**

#### 闸门C：审核闸门（Review Gate）
检查：
* Steam 商店页与 build checklist 是否都准备完。
* Google Play / Apple 需要的登录账号、审核说明、隐私政策、支持链接是否齐全。
* 权限申请与用途描述是否清楚。
* 需要截图、录屏、演示账号的地方是否提前准备。

判断标准：
**任何需要审核人员猜的地方，都是你的失职。**

#### 闸门D：验证闸门（Validation Gate）
检查：
* 内部测试、封闭测试是否覆盖关键机型和关键路径。
* 核心 smoke test 是否通过：启动、进局、广告、支付、存档、重开、设置、退出再进。
* 崩溃、ANR、严重卡死、首局阻断 bug 是否清零。
* 关键日志与埋点是否可读，首发后能不能判断问题。

判断标准：
**核心路径只要还有“可能翻车”，就不是 ready，是侥幸。**

#### 闸门E：运营闸门（Ops Gate）
检查：
* 是否明确 go/no-go 拍板时间。
* 发布后前 30-60 分钟谁盯数据、谁盯报错、谁负责回滚。
* 回滚条件是否提前写死，例如：
  * 崩溃率异常抬升
  * 广告/支付主链路失效
  * 首局无法完成
  * 大面积黑屏/卡死/无法登录
* 版本日志、渠道说明、应急沟通文案是否就位。

判断标准：
**没有 owner、没有监控、没有回滚阈值，就不叫上线计划，叫祈祷。**

### 5. 专门给独立游戏的“最小发布清单”
如果团队很小，不可能做大公司的厚文档，那就强制保住下面 16 条：

#### 发布前 72 小时
1. 锁版本，不再加系统级新功能。
2. 商店文案、截图、视频与实际版本逐项对照。
3. 隐私政策、用户支持链接、审核备注补齐。
4. 打包脚本和版本号检查一遍。

#### 发布前 48 小时
5. 内部测试包至少过一轮完整 smoke test。
6. 核心链路 bug 清到只剩可接受轻问题。
7. 广告、登录、支付、存档各过一轮真机验证。
8. 准备回滚包或上一个稳定版本。

#### 发布前 24 小时
9. 检查构建物哈希/包体/图标/渠道配置无误。
10. 确认审核账号、测试账号、演示说明可用。
11. 明确 go/no-go 时间和决策人。
12. 明确首发后 30-60 分钟谁盯什么。

#### 发布后 0-60 分钟
13. 检查安装、启动、进局、结算、重开是否正常。
14. 盯崩溃、ANR、报错日志和核心埋点。
15. 检查商店页是否展示正确、是否能搜到、版本是否真的生效。
16. 任何触发回滚阈值的问题，立刻执行，不拖。

### 6. 《光与朽》现在最该怎么落地
对《光与朽》这种独立项目，发布管理最该抓的不是复杂流程，而是这四刀：

#### 第一刀：先建《上线总清单》
不要把平台审核、素材、版本包、广告、商店文案散落在聊天记录和脑子里。直接做一张总表，列四列：
* 项目
* Owner
* 截止时间
* 是否阻断上线

#### 第二刀：把 smoke test 写成固定脚本
《光与朽》首发至少固定验证这些：
* 新安装启动
* 开一局
* 升级三选一
* 看广告复活
* 结算双倍
* 局外成长
* 退出重进存档正常
* 设置页正常

不写成脚本，最后一定漏。

#### 第三刀：平台资料前置
如果未来要上 Steam / Google Play / App Store，那现在就该同步准备：
* 商店页文案
* 核心截图
* 隐私政策
* 客服邮箱/支持页
* 审核说明
* 测试账号

别等功能差不多了才想起这些，晚了就会拖档期。

#### 第四刀：先写回滚标准
统一写死一句话：
**首发后如果出现“无法开始首局 / 广告主链路失效 / 大面积崩溃 / 关键平台拒审”，立即停止扩量或回滚。**

这不是悲观，这是专业。

### 7. 最适合我们的 go/no-go 会议模板（15 分钟版）
上线前开一次极短会议，只回答 7 个问题：
1. 本版功能是否已锁？
2. 商店页与实际版本是否一致？
3. 审核资料、登录信息、隐私链接是否全齐？
4. 核心 smoke test 是否全绿？
5. 当前还剩哪些 P1/P0 问题？
6. 回滚包和回滚动作是否已就位？
7. 如果今天不上，最大损失是什么；如果硬上，最大风险是什么？

只要第 4、5、6 任意一项答得虚，就别发。

### 8. 本课题的执行结论
真正高级的项目管理，不是把开发推进到“差不多做完”，而是把版本推进到**随时可审、随时可发、出事可撤**。

以后统一按这句话执行：

**“上线不是开发结束，而是一次带着审核、验证、监控、回滚一起发生的受控发布。”**

对《光与朽》来说，最值钱的动作不是再多做一个功能，而是立即建立：
* 一张上线总清单
* 一套固定 smoke test
* 一份平台审核资料包
* 一条明确回滚线

把这四样钉死，我们才是在做项目管理，不是在赌版本命。

## 课题：【专家进阶延展】单人项目的排期估算、缓冲设计与承诺管理：别再被“感觉快做完了”坑死

### 1. 为什么这是项目管理维度下一个真正未攻克的课题
路线图里已经覆盖了敏捷、Git/CI、MVP 边界、协同、风险预警、上线清单，但还有一个独立开发最常见、也最阴险的死因没被单独拆开：
**不会估时，不会留缓冲，还总爱对外先许诺。**

很多项目不是死在不会做，而是死在：
* 以为功能开发 2 天，实际上联调 + 测试 + 返工吃掉 5 天。
* 把“理想工期”当“承诺工期”。
* 每周都很忙，但上线时间反而越推越远。

所以这节课的核心不是教你“更精确预测未来”，而是教你：
**如何在高度不确定的单人开发里，用区间估算、显式缓冲和承诺闸门，把延期从玄学变成可控损耗。**

### 2. 2025-2026 的共识，很直接
最近两年关于项目估算的实务文章，虽然来自软件和游戏不同圈子，但结论高度一致：

1. **估算不是单点，是区间。**
   `最乐观 / 最可能 / 最悲观` 比一句“差不多两天”专业得多。
2. **缓冲不是浪费，是对不确定性的保险。**
   对定义清楚的任务，10%-20% 缓冲还算克制；高不确定、带新技术或多联动的任务，25%-50% 才正常。
3. **范围、时间、成本是三角，不存在白嫖。**
   加范围，就要延时间或加成本；压时间，就必须砍范围或接受风险。
4. **越早期，估算误差越大。**
   也就是经典的 Cone of Uncertainty。Backlog 还模糊时，任何精确到小时的排期都很装。
5. **单人项目要把测试、集成、真机验证、回归、恢复状态的时间单独算进去。**
   不然你算的只是“写代码时间”，不是“交付时间”。

### 3. 最新案例与可落地启发

#### 案例1：monday.com 2026 估算指南，直接给了缓冲区间
2026 年的项目估算指南把话讲得很清楚：
* **定义清晰、依赖少的项目**，可留 **10%-20% buffer**。
* **高不确定、带新技术或复杂依赖的项目**，建议 **25%-50% buffer**。

这对独立游戏尤其重要，因为《光与朽》这类项目里，真正贵的经常不是功能本身，而是：
* 广告 SDK 联动
* 真机验证
* 平台包体与配置
* UI/数值/存档互相牵扯

结论：
**以后别再给核心功能报“开发工时”，要报“可交付工时”。**

#### 案例2：ScrumExpert 2026，Backlog 越模糊，排期越虚
ScrumExpert 近期对 Cone of Uncertainty 的总结非常适合拿来打醒独立开发者：
* backlog 不清，schedule 风险就大；
* 早期估算天然高波动；
* 项目推进中，随着信息增加，估算区间才会收窄。

翻译成人话：
**在玩法、技术、资源都没锁死前，你没有资格给出像样的“准确日期”。**
最多只能给：
* 这一周验证什么
* 这个 Sprint 交什么增量
* 什么时候再重估一次

#### 案例3：Toño Game Consultants 2026，三角约束没有例外
Toño 在 2026 对 Triple Constraint 的解释很硬：
* scope 先转 effort，effort 再转 milestone；
* scope 增加，要么加时间，要么加成本；
* timeline 缩短，要么减 scope，要么接受更高风险。

这条对独立开发最值钱的地方是：
**别把“主人临时又想加一个功能”理解成小事。任何新增范围，都会吞掉时间或稳定性。**

#### 案例4：Wayline 2025，对 indie 开发者的提醒不是“多努力”，而是“估完必须加 buffer”
Wayline 在项目管理文章里专门提到：
* 任务要先拆小；
* 要先估时；
* **然后加 buffer**；
* 否则隐藏工作会把计划撕碎。

这其实就是独立项目最常见的血泪教训：
你以为只剩 20%，实际剩的是最后 50% 里最难啃、最容易返工的那一半。

### 4. 单人游戏项目里，最容易漏算的 8 种时间黑洞
以后估时，下面八项必须单独过一遍，不然全是自欺欺人：

1. **联调时间**：功能写完后，和已有系统对接要多久。
2. **真机验证时间**：不是编辑器能跑，是安卓/微信/抖音真机能跑。
3. **回归测试时间**：改一个按钮，可能炸结算、广告、存档。
4. **等待与切换成本**：找资源、改图、切上下文、重进状态。
5. **返工时间**：第一次方案很少就是最终方案。
6. **数据与配置时间**：数值表、资源引用、命名、平台配置都很吃时间。
7. **文档与交接时间**：尤其多人/多 Agent 协同时，没记录就会二次返工。
8. **恢复专注时间**：单人开发最贵的其实是被打断后重新进入状态的损耗。

### 5. 最实用的估算框架，不要复杂，要能天天用

#### 框架A：三点估算（O / M / P）
每个任务都写三档：
* **O（Optimistic）最乐观**：一切顺利，多快能做完。
* **M（Most Likely）最可能**：正常情况要多久。
* **P（Pessimistic）最悲观**：出联动、返工、配置问题时多久。

独立开发不需要搞太学术，直接记一句：
**承诺工期 = M + 风险缓冲，而不是 O。**

如果任务跨系统、跨平台、第一次做，直接用 P 去看有没有必要先砍范围。

#### 框架B：任务分级缓冲法
把任务粗暴分三类：

* **A级，低不确定**：纯熟悉活，缓冲 10%-15%
  * 例：改一个已验证的 UI 文案、补一个小配置
* **B级，中不确定**：有联动但路径清楚，缓冲 20%-30%
  * 例：接一个新装备效果到现有战斗
* **C级，高不确定**：首次尝试、跨平台、跨 SDK、跨系统，缓冲 35%-50%
  * 例：奖励广告 + 复活逻辑 + 存档恢复 + 埋点一起上

以后谁再说“这功能应该两天能搞定”，先问一句：
**它是 A、B 还是 C？**

#### 框架C：承诺闸门（Commitment Gate）
任何对外承诺前，先过三问：
1. 这个任务有没有最小可运行定义？
2. 有没有把测试和回归算进去？
3. 有没有至少一档显式缓冲？

三问里有一条答不清，就别给日期。

### 6. 最适合《光与朽》的排期法，不是“排满”，是“只排会交付的那一层”
《光与朽》现在已经不适合用“把所有想做的东西排满日历”这种傻办法。更稳的做法是三层排期：

#### 第一层：承诺层（本周必须交）
只放 1 个核心里程碑，最多 2 个。
例如：
* 安卓测试包稳定打出
* 失败复活广告完整跑通

#### 第二层：预备层（做完再拿）
一旦承诺层提前完成，再补这些。
例如：
* 结算双倍广告优化
* 局外提示红点补齐

#### 第三层：欲望层（只记，不碰）
所有新想法、包装、美化、优化都进 backlog，不进本周承诺。

这套排法的价值是：
**你永远先保交付，再谈惊喜。**

### 7. 给单人游戏项目的“周排期模板”
以后每周排期，统一按下面这张小表来：

#### 本周 Sprint 计划
* **本周唯一核心结果**：
* **必须完成（1-2项）**：
* **可选完成（1-2项）**：
* **明确不做**：
* **本周最大风险**：
* **预留缓冲**：至少半天到一天
* **周五验收标准**：截图 / 真机包 / 视频 / 可复现步骤

重点是：
**缓冲必须先占坑，不是忙到爆炸后再说“怎么没时间了”。**

### 8. 什么时候该重估，而不是硬顶
以下情况出现任一条，就别再死撑原计划，立刻重估：

1. 某核心任务实际耗时超过 M 的 1.5 倍。
2. 出现新的跨系统依赖。
3. 同一任务返工两次以上。
4. 真机 / 平台验证暴露新阻断。
5. 本周承诺层有一项开始滑移。

重估不是认输，是在避免更大的假进度。

### 9. 《光与朽》现在就能直接落地的狠招
对我们现在的项目，我建议立刻执行这四刀：

1. **所有任务卡增加“估算级别(A/B/C)+缓冲”字段。**
2. **周计划只承诺一个核心版本结果。**
3. **任何跨广告、存档、打包、审核的任务，默认按 C 级估时。**
4. **每周五复盘“估时偏差最大的三个任务”，下周校正。**

别再问“为什么总感觉忙但版本没前进”。
答案通常就两条：
**第一，没把隐藏工时算进去；第二，把欲望清单当承诺清单了。**

### 10. 本课题的执行结论
真正成熟的项目管理，不是把工期说得很漂亮，而是敢把不确定性明码标价。

以后统一按这句话执行：

**“估算报区间，承诺看中位，排期先留缓冲，新增需求必须拿别的东西来换。”**

对《光与朽》来说，这不是纸上谈兵。
这是避免我们在 4 月上线前，被“差一点就做完”这种狗屁幻觉狠狠干死的唯一办法。

## 课题：【专家进阶延展】依赖管理与关键路径控制（Critical Path）：为什么大家都在忙，版本还是卡死

### 1. 为什么这是项目管理维度下一个真正未攻克的课题
前面我们已经学了敏捷、Git/CI、MVP 边界、协同、风险预警、上线清单、估时缓冲，但还缺一把非常致命的刀：
**如何识别哪些任务真的在推动上线，哪些只是看起来很忙。**

项目延期很多时候不是因为工作量太大，而是因为**关键依赖没被识别、关键路径没被优先保证、非关键任务反而吃掉了主线资源**。对独立游戏尤其致命，因为你只有一个脑子、一套手、一条时间线，任何主链路卡住，其他努力都会变成伪进度。

所以这个课题的核心不是“把任务排得更漂亮”，而是：
**找出那条一旦延误就会直接拖延上线的最长依赖链，并用最狠的优先级把它保护起来。**

### 2. 2025-2026 的新共识：关键路径不是大公司术语，而是独立项目防暴毙的生死线
根据 Asana、Atlassian、monday 和 Wayline 在 2025-2026 的文章，核心结论高度一致：

1. **关键路径 = 从开始到结束，最长的一串相互依赖任务。** 这条链上任一节点晚了，整个项目就晚。
2. **依赖管理不只是“谁先谁后”，还包括资源、审批、跨模块、外部平台、最佳实践等多种依赖。**
3. **很多延期不是因为关键任务难，而是因为团队把大量时间花在“非关键但舒服”的工作上。**
4. **关键路径只能盯时间，不会自动解决资源冲突，所以必须配合资源倾斜与任务冻结。**
5. **里程碑要围绕关键路径设计，不然 milestone 看起来很满，主线却没前进。**

翻译成人话就是：
**不是所有待办都值同样的命。能阻断上线的那条链，优先级必须永远高于一切 polish。**

### 3. 依赖到底该怎么分，才不会漏掉真正的炸点
monday 2026 对依赖分类很实用，放到游戏项目里几乎能直接照搬：

#### A. 逻辑依赖（Logical Dependency）
任务天然有前后顺序，不能乱。
* 例：先有战斗框架，后有技能接入；先有局内结算，后有广告复活。

#### B. 资源依赖（Resource Dependency）
不是不会做，而是缺人、缺素材、缺设备、缺时间。
* 例：UI 不能接，因为图还没切；打包不能测，因为证书或 SDK 还没配。

#### C. 审批/验收依赖（Approval Dependency）
功能写完了，但还不能进主线，因为必须验收、过审、拍板。
* 例：商店文案要先确认；付费点位要主人最终拍板；广告位设计要过体验验收。

#### D. 跨模块依赖（Cross-team / Cross-system Dependency）
一个模块的变化会卡住另一个模块。
* 例：数值方案没定，UI 展示和敌人强度都不敢锁；存档结构一改，奖励结算和广告恢复都得跟着动。

#### E. 外部依赖（External Dependency）
项目外部世界卡你脖子。
* 例：Steam/Google/Apple 审核、第三方广告 SDK、支付配置、外包素材交付。

真正危险的，不是这些依赖本身，而是**你没有把它们显式写出来**。只要依赖留在脑子里，它迟早会在最不该炸的时候炸。

### 4. 关键路径真正的用法，不是画图，是决定“谁先活”
Asana 与 Atlassian 的共识都很明确，CPM 的作用不是做出一个很专业的流程图，而是帮助你回答三个问题：

1. **哪些任务真的不能晚？**
2. **哪些任务有 float（浮动/缓冲）可以晚一点？**
3. **哪些事情其实能并行，不该傻乎乎串着做？**

#### 什么是 Float（浮动时间）
Float 指某个任务在不影响最终交付日期的前提下，最多能拖多久。

这概念非常值钱，因为它告诉你：
* **零浮动任务** = 真正的关键任务，别碰、别插队、别打断。
* **有浮动任务** = 可以让路，必要时延后，给主链路让资源。

独立开发最常见的蠢死法就是：
**把零浮动任务和高浮动任务混着做，最后把真正该先做的主链路拖死。**

### 5. 2025-2026 最新案例与实操启发

#### 案例1：Wayline 2025，《The Critical Path Problem: Why Indie Game Timelines Always Derail》
Wayline 这篇文章几乎是给独立开发者当头一棒。它指出 indie 项目时间线反复失控的根因，往往不是努力不够，而是：
* 低估依赖链长度
* 把可并行工作串行化，白白拖长工期
* 没看见隐藏依赖，比如测试、集成、调优、平台适配
* 没有及时重算关键路径，导致旧计划失真后还在继续执行

最值钱的启发：
**关键路径不是开局算一次就完事，它必须随着新需求、返工和阻塞动态更新。**

#### 案例2：Wayline 2025，《Game Project Milestones: Efficient Planning for Indie Game Developers》
这篇文章强调：
* milestone 必须拆成可验证小节点
* 开始一个任务前，必须确认前置条件是否真的满足
* 依赖不清会直接制造返工和瓶颈

这和我们前面学的风险预警是完全闭环的：
**里程碑如果不绑依赖，里程碑就是假的。**

#### 案例3：Asana 2026，CPM 与 float 的实操价值
Asana 2026 版 CPM 指南最有用的点不是定义，而是方法：
* 先列出全部活动
* 标清依赖
* 建网络图
* 估时
* 找最长路径
* 算 float

并且它明确提醒：
**CPM 非常依赖估时准确度，也不自动处理资源可用性。**
这句话对我们太关键了，因为游戏项目里“一个人同时干十件事”的现实，意味着就算逻辑上能并行，资源上也未必能并行。

#### 案例4：monday 2026，依赖管理不是流程洁癖，而是风险控制
monday 对依赖管理的价值总结得很准：
* 能更早暴露 bottleneck
* 能提前做 contingency plan
* 能优化资源分配
* 变化发生时更快定位受影响链路

翻译成项目动作就是：
**一旦关键节点卡住，不要问‘最近大家在忙什么’，要问‘哪条依赖链断了’。**

#### 案例5：Atlassian 2026，关键路径适合严格截止期，但不能僵化执行
Atlassian 的提醒也很重要：
* CPM 对复杂依赖、硬 deadline 的项目最有价值
* 但如果范围与优先级频繁变动，固定关键路径会迅速过时

这意味着独立项目不能把 CPM 当雕像供着，而要把它当活地图。每次砍功能、改范围、插入新平台需求，都必须重算主链路。

### 6. 最适合独立游戏的“轻量关键路径法”
大公司会画完整网络图，独立项目没必要那么重。我们要的是能天天用、不会死在维护成本上的版本。

#### 第一步：先写“上线倒推链”
不是从 backlog 往下排，而是从“要上线”倒推：
1. 可发正式包
2. 发布前 smoke test 通过
3. 安卓/iOS/Steam 构建稳定
4. 商业化主链路可跑（广告/支付）
5. 战斗主闭环稳定
6. 核心内容边界锁死

这串链就是候选关键路径骨架。

#### 第二步：给每个节点补前置条件
例如“广告复活可跑”前面可能依赖：
* 局内失败状态机稳定
* 结算与复活逻辑分离
* 广告 SDK 接入完成
* 异常分支处理完成
* 真机测试通过

一补前置条件，真正的关键路径就会冒出来。

#### 第三步：标记零浮动任务
问自己一句：
**“这个任务如果晚两天，会不会直接推迟上线？”**

* 会 → 关键路径任务
* 不会 → 非关键任务

#### 第四步：把非关键任务明确降级
非关键任务不是不要做，而是：
* 不许抢主链路时间
* 不许在关键节点周插队
* 不许制造额外测试量

#### 第五步：每周重算一次
只要出现以下任一情况，就必须重算：
* 新增系统需求
* 某任务返工两次以上
* 外部依赖延迟
* 平台规则变化
* 主链路阻塞超过半天

### 7. 最适合《光与朽》的关键路径拆法
如果以当前项目为目标，我们最该盯的不是“所有功能进度”，而是下面这条最可能的上线关键路径：

1. **核心战斗闭环稳定**
   * 激光命中反馈、敌人波次、失败结算、再来一局完整跑通
2. **局内成长与 Build 选择可验证**
   * 至少一套可感知差异的成长三选一
3. **广告主链路稳定**
   * 失败复活、结算双倍、失败/跳过/加载异常都可处理
4. **存档与局外最小成长稳定**
   * 不会因重进、异常退出把局外状态搞炸
5. **安卓一键打包稳定**
   * 每周可连续产出测试包
6. **上线 smoke test 固化**
   * 启动、开局、升级、看广告、结算、退出重进全绿
7. **商店/平台资料同步准备完**
   * 截图、文案、隐私、审核说明不掉链子

而下面这些大概率不是当前关键路径：
* 额外视觉 polish
* 大量支线敌人/皮肤
* 花哨外层系统
* 不影响首发验证的 meta 扩展

所以以后别再被“这个也只要半天”骗了。**半天加在非关键任务上，也是在偷关键路径的命。**

### 8. 一套真正能执行的“依赖审查清单”
以后每周排期或新功能立项前，统一过这 8 个问题：

1. 这个任务的前置条件是什么？
2. 它卡住了谁，谁又卡住它？
3. 它属于逻辑、资源、审批、跨模块还是外部依赖？
4. 它晚 1 天会不会直接推迟上线？
5. 它能并行吗，还是必须串行？
6. 它的隐藏依赖是什么（测试、配置、打包、资源、审核）？
7. 若主链路今天爆炸，这个任务能否立刻暂停？
8. 它完成后的验收输出是什么？

只要第 1、4、6 题答不清，这个任务就不该直接开做。

### 9. 最值钱的 5 条执行铁律
1. **先保关键路径，再谈高质量非关键任务。**
2. **任何新增需求都必须说明它插入哪条依赖链，会不会挤压主链路。**
3. **零浮动任务禁止被日常杂务切碎。**
4. **所有外部依赖都要有替代方案或缓冲。**
5. **每周复盘不是看做了多少，而是看关键路径缩短了没有。**

### 10. 本课题的执行结论
真正成熟的项目管理，不是把每个人都安排得很忙，而是把那条决定上线死活的最长依赖链狠狠干通。

以后统一按这句话执行：

**“不在关键路径上的忙，大概率只是好看的伪进度。”**

对《光与朽》来说，接下来最该做的不是再铺更多待办，而是马上画出上线关键路径，把广告、战斗、打包、存档、审核资料这些零浮动任务钉死，然后让一切非关键工作统统让路。

## 课题：【专家进阶延展】资源约束与瓶颈管理（TOC + WIP限制）：为什么大家都很忙，版本却还是出不来

### 1. 为什么这是项目管理维度下一个真正未攻克的课题
前面已经学了敏捷、Git/CI、MVP 边界、协同、风险预警、上线清单、估时缓冲、关键路径，但还有一个独立项目最容易被忽视的死穴：
**不是所有低效都来自计划差，很多低效来自系统里永远只有一个地方真正决定吞吐。**

这就是瓶颈。对单人或超小团队来说，瓶颈可能不是“人不够”，而是：
* 美术资源出图太慢，程序干等
* 广告/打包/真机验证都卡在同一个人身上
* 一次同时开太多任务，谁都没真正做完
* 每个模块看着都在推进，但真正能合包上线的工作极少

所以这节课的核心不是“更努力”，而是：
**识别系统当前唯一最卡的约束点，然后让整个项目围着它优化，而不是所有人各忙各的。**

### 2. 2025-2026 的方法论共识，很硬
最近两年关于 bottleneck、WIP limit、capacity planning 的文章，虽然来自软件、Kanban 和游戏开发不同圈子，但结论几乎一致：

1. **真正拖慢交付的，通常不是平均效率，而是最慢那一道工序。**
2. **提高非瓶颈效率，常常只会制造更多堆积，不会提升最终吞吐。**
3. **WIP（在制品）过多会掩盖瓶颈，让团队误以为“大家都很忙所以没问题”。**
4. **瓶颈必须被显式可视化，否则返工、等待、上下文切换会把真实问题藏起来。**
5. **约束点会移动，所以项目要持续重识别，而不是一次诊断后永久有效。**

Atlassian 在 2026 年关于项目瓶颈的文章里把原因拆得很清楚，常见延误源包括：资源不足、流程低效、沟通链过长、依赖混乱、审批等待。它真正有价值的一句提醒是：
**加资源前先判断，新增资源到底能不能打掉约束，还是只会把瓶颈推到下游。**

Atlassian 在 2025 年更新的 WIP limits 指南里也讲得很直白：
**WIP 限制的价值不是让看板好看，而是强迫瓶颈与阻塞暴露出来，并促使团队围绕当前卡点协同增援。**

### 3. 先下结论：项目管理不是让每个人 100% 忙，而是让“可交付吞吐”最大化
很多独立项目会陷入一个假勤奋陷阱：
* 同时开 8 个功能
* UI 改一点，数值调一点，广告接一点，特效磨一点
* 每天都很忙
* 但一周后没有一个完整闭环能验收

这就是典型的**资源效率思维**，不是**流动效率思维**。

资源效率思维追求的是“手别闲着”。
流动效率思维追求的是“一个完整结果尽快穿过系统”。

对游戏项目，后者更值钱。因为：
**能跑通一个完整闭环，比十个半成品模块高级得多。**

### 4. 瓶颈怎么识别，不靠感觉，靠四个信号

#### 信号A：任务堆积最多的阶段
哪个阶段的任务总是在排队，哪个地方大概率就是瓶颈。
例子：
* 大量功能“代码完成”但都在等美术资源
* 大量版本“功能完成”但都卡在真机验证或打包
* 大量内容“需求明确”但都在等你本人拍板

#### 信号B：返工和等待最多的阶段
真正可怕的瓶颈不一定是最慢的，也可能是**让别人反复返工**的地方。
比如：
* 需求定义太模糊，导致外包/Agent 反复重做
* 美术标准没写死，资源导入后还要重切重命名
* 广告或存档逻辑没有统一验收标准，程序改一轮炸一轮

#### 信号C：系统里最不可替代的人/技能
如果某个阶段只有一个人能做，而且谁都绕不过，那它天然就是高风险瓶颈。
对独立项目最典型：
* 主人负责所有 UI 与美术整合
* 我负责代码、构建、脚本和流程文档
* 打包、审核、商店配置只有一个人懂

这类瓶颈最危险，因为它一旦被打断，整条链都停。

#### 信号D：完成态最少的地方
不要看“做了多少”，看“真正 Done 了多少”。
如果一个环节总把工作变成“90% 完成”，那它就在吃项目命。

### 5. 2025-2026 最新案例与实操启发

#### 案例1：Atlassian（2026）——别把“资源不够”当默认答案
Atlassian 2026 的 bottleneck 文章把一个很常见的蠢判断拆穿了：很多团队一看到延误，就本能地想加人、加预算、加工具。但如果你没确认真正约束点在哪里，新资源大概率只是把堵塞往后推。

可落地启发：
1. 先定位卡点是在需求、生产、验证还是发布。
2. 只给约束点加资源，不给全系统盲目加资源。
3. 加资源后继续观察，确认吞吐有没有真的提升，而不是只让前序阶段更忙。

#### 案例2：Atlassian（2025）——WIP 限制的价值，在于逼团队停止“多开假勤奋”
Atlassian 2025 的 WIP 指南强调，WIP 限制会让阻塞和瓶颈变得可见，一旦某个状态爆满，团队就该围绕那个状态去清障或补能力，而不是继续开新任务。

这对独立游戏尤其值钱，因为单人/双人项目最容易犯的错就是：
**遇到卡点，不是解决它，而是转头去开一个新任务，制造更多半成品。**

可落地启发：
* 任何时刻，开发中任务上限必须被钉死。
* 卡住时先清旧任务，不准拿新任务麻痹自己。
* 若某状态长期爆满，要么补技能冗余，要么重构流程。

#### 案例3：GitScrum（2026）——游戏项目里最常见的瓶颈不是代码，而是美术流水线不可见
GitScrum 2026 的游戏 PM 页面提到一个非常典型的现象：传统项目报告会写“美术完成 60%”，但这句话毫无意义，因为真正卡住项目的不是总百分比，而是具体阶段，比如概念图未审、贴图被打回、Boss 模型未开工、动画还没入游戏。

这和游戏项目现实完全一致。真正的瓶颈常出现在：
* 概念审批
* 切图导出
* 规范化命名
* 入 Unity 后适配
* 动画或特效联动

可落地启发：
**不要再用“整体完成度”汇报美术，要按阶段状态看：概念、制作、导出、导入、联调、入包。**

#### 案例4：Wayline（2025）——真正的瓶颈常来自“创意愿景”和“技术现实”的冲突
Wayline 在 2025 年谈游戏开发瓶颈时，核心判断很准：很多团队以为自己卡在执行，实际上卡在愿景过大、依赖不清、前置条件没满足却强行开工，最后制造返工与堆积。

它给的启发非常适合我们：
* 不满足前置条件的任务，不要开。
* 大目标必须拆成能过里程碑的小段。
* 一切 scope 增长都会把瓶颈放大。

### 6. 独立游戏最实用的“TOC 五步法”
把 Theory of Constraints 翻译成人话，就是下面五步：

#### 第一步：找当前唯一主瓶颈
不是找十个问题，先找一个最限制吞吐的点。
例如现在《光与朽》可能的主瓶颈是：
* UI/美术资源接入速度
* 广告主链路验证
* 安卓稳定打包
* 主玩法调优与真机反馈回路

#### 第二步：榨干瓶颈产能
如果某处是瓶颈，就别让它被杂事切碎。
例子：
* 如果打包验证是瓶颈，就把打包环境、脚本、版本号、日志流程全标准化
* 如果美术接入是瓶颈，就把尺寸、命名、导出格式、Prefab 对接先写死

#### 第三步：让非瓶颈为瓶颈服务
这一步最反人性，但最有效。
如果瓶颈在美术接入，那程序就不该继续疯狂开新需要新资源的功能；应该优先做可复用框架、占位适配、导入工具。
如果瓶颈在广告验证，那别再磨支线特效，先把真机验证链和异常分支跑通。

#### 第四步：抬高瓶颈能力
当你已经把流程收紧了，仍然卡，就该加能力：
* 模板化
* 自动化
* 技能冗余
* 外包切分
* Agent 分工

#### 第五步：瓶颈转移后，重新识别
一旦原瓶颈被打掉，项目的主约束会转移到别处。不要抱着旧判断不放。

### 7. 最适合独立团队的 WIP 限制法，不搞复杂，直接砍
给《光与朽》这类项目，最稳的规则不是大公司那种厚流程，而是三刀：

#### 刀1：同时“开发中”的大任务不超过 2 个
超过 2 个，大概率就会变成上下文切换地狱。

#### 刀2：任何“等待中”任务超过 24 小时，必须升级处理
等待不是自然状态，等待就是项目正在失血。

#### 刀3：没到 Done 的功能，不算进度
什么“差一点”“基本好了”“就剩收尾”，全是废话。没过验收就是没完成。

### 8. 给《光与朽》的具体应用，别空谈
如果把这套瓶颈管理直接套到《光与朽》，我判断当前最该盯的是这四类约束：

1. **主玩法调优闭环**
   * 不是多做内容，而是战斗反馈、成长选择、失败重开能不能快速验证。
2. **广告与商业化验证链**
   * 奖励广告、复活广告、异常回退都属于高风险瓶颈，必须优先形成稳定模板。
3. **美术/UI 接入流水线**
   * 主人这边如果继续靠临时切图、临时改尺寸、临时重命名，整个版本节奏会一直被拖。
4. **一键打包与真机检查**
   * 如果每次出测试包都像开盲盒，整个项目的学习速度就会被压死。

### 9. 立刻能执行的 7 条铁律
1. **每周只指定一个主瓶颈，不要同时打十个点。**
2. **所有任务卡增加“当前卡在哪个阶段”字段。**
3. **停止用百分比汇报，改用阶段状态汇报。**
4. **开发中任务上限 2 个，等待中任务上限 1 个。**
5. **瓶颈环节优先吃整块时间，不要被碎事切烂。**
6. **非瓶颈工作必须给瓶颈让路。**
7. **每周复盘时只问一句：这周我们提升的是吞吐，还是只是提升了忙碌感？**

### 10. 本课题的执行结论
真正成熟的项目管理，不是所有人都忙到飞起，而是系统里最慢那一环被盯死、被保护、被强化。

以后统一按这句话执行：

**“瓶颈不解决，其他努力大多只是制造库存；WIP 不受控，忙碌感就会伪装成进度。”**

对《光与朽》来说，下一步最值钱的动作不是再铺更多功能，而是先把：
* 主玩法验证
* 广告主链路
* 美术接入
* 打包真机检查
这四条链里当前最慢的一环狠狠干透。

只有这样，版本才会真的往上线移动，而不是在一堆半成品里原地打转。

## 课题：【专家进阶延展】垂直切片里程碑管理（Vertical Slice Milestone Management）：如何把“能玩原型”推进成“能验证、能展示、能决策”的小闭环

### 0. 为什么把它定为“下一个未攻克课题”
路线图里“敏捷极简应用”“Git流与CI/CD”“MVP边界”“外包/兼职/多Agent协同”这四个主课题已经覆盖；但对我们现在最要命的，不是再学一套抽象框架，而是把 **7天垂直切片** 真正做成一个可管理、可验收、可拿来做测试与合作判断的里程碑。

所以，项目管理维度下的下一个关键缺口，我定为：
**垂直切片里程碑管理（Vertical Slice Milestone Management）**。

这不是重复讲MVP，而是解决一个更现实的问题：
**原型能玩，不等于项目能推进；只有当一小段体验同时跑通玩法、反馈、美术、性能、打包、测试、展示素材，团队才真正知道项目能不能继续投。**

---

### 1. 先下结论：垂直切片不是“做一个好看的Demo”，而是“用最小但完整的生产链验证项目值不值得继续”
根据 Toño Game Consultants（2024/2025）、Xsolla（2024）、IndieGames101（2024）、Playstack 在 devcom 2025 的议题，以及 Walla Walla Studio 的 2025 生产文章，行业里对 Vertical Slice 的共识越来越明确：

1. **Prototype 原型** 解决“这个点子可能有趣吗？”
2. **MVP** 解决“最少功能能否形成价值闭环？”
3. **Vertical Slice** 解决“这个项目能否以接近最终品质的小样本被稳定生产、验证、展示、推销、扩展？”

所以垂直切片本质上是一个 **生产性里程碑**，不是单纯的设计里程碑。

它必须同时回答五个问题：
- 核心乐趣在接近成品品质下还成立吗？
- 真实制作链路能不能跑通？
- 这个体验是否足够拿去做外部测试/发行沟通？
- 继续扩内容时，成本和节奏是否可预测？
- 现有项目是否应该继续、转向，还是直接砍？

说白了：
**垂直切片不是为了证明你会做游戏，而是为了证明这项目值得继续烧时间。**

---

### 2. 最新行业信号：2025 之后，Vertical Slice 的标准明显变严了

#### 信号A：发行与融资方更看重“可判断的切片”，不是概念图和PPT
Playstack 在 devcom 2025 的分享介绍里明确强调：
- 他们评估过大量 vertical slices；
- 切片越来越成为吸引发行方注意力的关键材料；
- 关键不只是“有内容”，而是 **核心支柱是否被选对、是否有足够打磨、是否能被清晰展示**。

这说明现在外部决策者的判断逻辑已经升级了：
**他们不要“看起来有潜力”的项目，他们要“看得出生产判断能力”的项目。**

#### 信号B：高压切片交付正在变成“开发+营销并行”的小型战役
Walla Walla Studio 在 2025 年文章里给出的做法很硬：
- 一开始就锁定不可动摇的范围；
- Day 1 就搭 CI 与性能遥测；
- 用 12 周节奏、每周 gate 验收；
- 每周都要求产出 capture-ready build（能稳定录屏、出截图、对外展示）；
- 开发、美术、社区、营销资产并行准备。

这很关键。它说明现代 vertical slice 已不是“开发做完后再包装”，而是：
**从第一周开始就把“可展示性”纳入项目管理目标。**

#### 信号C：小团队越来越把 Story Mapping 当成垂直切片前置工具
Toño Game Consultants 在 2025 年的 Story Mapping 文章里把它说得很直：
- 小团队缺 producer 时，最容易掉进 scope creep；
- Story mapping 的价值不是写待办，而是按玩家旅程看功能；
- 它是 prototype 到 vertical slice 的桥；
- 没有故事地图，切片很容易变成 feature soup（功能大杂烩）。

这对独立开发尤其重要：
**切片的管理单位不该是“功能列表”，而应该是“玩家在这一小段里经历了什么”。**

#### 信号D：软件交付研究继续证明：小批量交付不是慢，而是更稳
DORA 2026 指南明确提出：
- 速度和稳定性长期不是对立项；
- 提升交付表现的常见方法之一就是 **减少批量（small batches）**；
- 小改动更容易理解、测试、恢复，也更容易形成高吞吐且低事故率的交付节奏。

把这个思想翻译到游戏切片管理里，就是：
**不要等“这一大坨都好了”才集成；切片必须由多个小而完整的可验收小片段堆起来。**

---

### 3. 关键认知：Vertical Slice 管理的目标，不是“做一关”，而是“证明复制规律”
很多人把垂直切片理解成“先做一小段完整内容”。这只说对一半。

真正更值钱的是：
**通过这段小内容，测出未来规模化生产的规律。**

根据 Xsolla 与 IndieGames101 的说法，切片应该帮助团队校准：
- 真实预算
- 真实品质标准
- 真实产能
- 真实风险

IndieGames101 甚至给了一个很硬的判断：
**如果切片做完后，预算预估偏差超过 10%，那原来的生产计划就该重做。**

这句话很毒，但非常对。
它提醒我们：
垂直切片完成后，最重要的输出不只是 build，还是三件事：
1. **复制一份同等质量内容，需要多久？**
2. **哪些环节最卡？**
3. **哪些东西根本不该继续做大？**

如果切片没产出这三条，说明这个里程碑只是在“做样子”。

---

### 4. 一套适合独立游戏/小团队/多Agent协同的垂直切片里程碑框架

我建议把 Vertical Slice 里程碑拆成下面 6 个管理层：

#### 第一层：Slice Charter（切片任务书）
在动工前，必须写一页任务书，只回答下面 6 个问题：
1. 这个切片服务谁？内部决策、陌生用户测试、发行沟通，还是广告素材验证？
2. 这段切片要证明哪 2-3 个核心支柱？
3. 这段体验的开始、高潮、结束分别是什么？
4. 哪些内容必须接近成品品质？
5. 哪些内容允许占位或半成品？
6. 到什么程度就算“通过/不通过”？

没有这页纸，项目极容易一边做一边漂。

**推荐模板：**
- 目标受众：
- 要验证的核心假设：
- 必保留支柱：
- 明确排除项：
- 计划时长：
- 通过标准：
- 失败标准：

#### 第二层：按玩家旅程做 Story Map，不按部门列任务
别写“做UI / 做特效 / 做敌人”。
要写成：
- 玩家进入战斗后 10 秒内看懂局面
- 玩家在第一次压线时学会调位/补救
- 玩家在第一次强化选择时感知 build 分叉
- 玩家在第一次失败后愿意立即重开

然后再把这些体验节点拆给程序、美术、音频、QA、Agent。

这是切片项目管理最重要的一刀：
**先定义体验，再分派工种；不要先分工种，再希望体验自己长出来。**

#### 第三层：每个节点都要有 Definition of Done（完成定义）
Toño 在 story mapping 里强调得很对：故事没有 DoD，等于没写。

对切片来说，DoD 至少要含这五条：
- 功能跑通
- 输入/反馈完整
- 无阻断级 bug
- 录屏可用
- 可进入主分支或演示分支

如果是给外部测试/合作看的切片，再加两条：
- 首次体验无需口头解释也能推进
- 崩溃率、卡顿和加载时间在可接受范围内

#### 第四层：切片必须按“可录制 Gate”推进
Walla Walla 提到 capture-ready weekly gates，这个非常狠，建议直接抄。

对小团队可简化为 4 个 Gate：

**Gate 1：玩法骨架可跑**
- 从进入到结束有闭环
- 可以死、可以赢、可以重开
- 允许丑，但不能断

**Gate 2：核心爽点可感知**
- 至少一个高光瞬间成立
- 至少一个失败教训可理解
- 关键反馈已接上

**Gate 3：展示品质可成立**
- 有可用UI、音频、屏幕反馈
- 有3段可录制片段
- 性能不会一录就炸

**Gate 4：外部验证可执行**
- 陌生人能上手
- 能收集结构化反馈
- 能输出“继续 / 转向 / 砍掉”的决策

注意，Gate 不是进度汇报，它是 **准入制度**。
没过 Gate，就不进入下一层打磨。

#### 第五层：以小批量集成替代“大合并”
用 DORA 的 small batches 思想，切片阶段强制规定：
- 每个改动必须能在 0.5-1 天内集成验证
- 每次提交只解决一个体验节点或一个明显缺口
- 不允许堆 3 天再一起合并
- 每天至少产出一个可运行 build

对独立开发这看起来麻烦，实际上省命。
因为切片阶段最贵的不是开发，而是 **最后发现所有东西接不上**。

#### 第六层：切片结束后必须做“复制率复盘”
切片验收后，不要马上冲下一块内容。
先做 30 分钟复盘，至少回答：
1. 同质量再复制一块，需要多久？
2. 哪个环节最不稳定？
3. 哪个资源最缺？
4. 哪个支柱最值钱？
5. 哪个看着酷但不值得继续？

这一步决定后续排期是否靠谱。
没有复盘，切片就只是一次华丽自欺。

---

### 5. 实操清单：如何把切片管成“决策工具”而不是“艺术品”

#### 清单A：切片前
- 写 1 页 Slice Charter
- 明确目标受众（自己/陌生玩家/发行/广告测试）
- 列出 2-3 个必须验证的核心支柱
- 写清楚排除项
- 确定 1 个演示分支或稳定主分支策略
- 配置最小 CI / 自动打包 / 错误日志

#### 清单B：切片开发中
- 每日只推进 1 个体验节点
- 每 1-2 天输出一次可录制 build
- 关键节点都要录 10-20 秒短视频留档
- 每周做一次 scope 审判：新增项全部过“它验证什么”这道门
- 性能、输入、UI、音频至少每 2 天回归一轮

#### 清单C：切片验收时
- 陌生人能否在 30-60 秒内理解目标
- 是否出现至少一次“卧槽这一下挺爽”
- 失败后是否知道下一把怎么改
- 是否能产出 3 个可传播素材点
- 是否能估算复制下一块内容的真实成本

#### 清单D：切片后
- 更新路线图：继续 / 转向 / 停止
- 重估工期与预算
- 把“切片里临时糊的屎”单独列债务，不准混进已完成
- 把切片素材转成测试包、商店页素材或合作沟通材料

### 6. 常见致命错误

#### 错误1：把切片做成“开场教学”
IndieGames101 提到一个很关键的点：
切片最佳位置通常不是最开头，而是 **late early-game / early mid-game**。
原因很简单：
- 太前面全是教学，爽点露不出来；
- 太后面能力太复杂，陌生人看不懂。

对独立项目来说，最稳的是：
**挑玩家已经稍微有能力、但还没复杂到爆炸的那一段。**

#### 错误2：做成“美术样片”，没证明核心循环
好看不等于能继续做。
如果核心循环、失败反馈、重开动机、性能稳定性都没证实，只有美术更精致，那只是昂贵幻觉。

#### 错误3：靠英雄模式硬赶
Walla Walla 直接点破：
很多切片是靠团队透支、爆肝、临时修补赶出来的。这种切片即便看起来好，也不能代表真实产能。

所以切片必须记录：
- 哪些内容是可复制流程产出的
- 哪些内容是临时手搓救火的

否则你拿切片估产能，结论一定失真。

#### 错误4：没有明确占位策略
切片不是要求所有东西都最终品质，而是要求：
**该高品质的部分足够高品质，不重要的部分明确承认还没做。**

占位内容必须“看得出是占位”，别做成半吊子伪成品，最容易误导判断。

#### 错误5：切片过了，却没有改排期
如果切片暴露了流程慢、资产贵、性能差，但项目计划完全不变，那切片白做。

### 7. 对《光与朽》与后续 7 天原型链路的直接应用

#### 对《光与朽》
如果我们现在要做《光与朽》的下一轮验证，切片不该选“新手第一关教程”，而该选：
- 玩家已经拿到基础激光塔与一次 build 分叉；
- 能在 3-5 分钟内经历一次压线危机、一次布局修正、一次明显强化；
- 最后用一个 Boss / 精英波把“摆位 + 折射 + 流派选择”的价值狠狠干出来。

这个切片必须验证四件事：
1. 激光折射到底是不是传播级爽点；
2. 玩家失败后是否知道问题出在布局还是选择；
3. 一局内的 build 分叉是否足够清晰；
4. 这套体验是否能剪出 3 条好素材。

#### 对后续 7 天垂直切片选型
我们之后做 AI 视频反向立项时，切片里程碑不该写成“第3天把系统做完”，而该写成：
- Day 1：跑通主交互骨架
- Day 2：做出一个高光瞬间
- Day 3：接上失败反馈和重开
- Day 4：补 UI/音频/镜头反馈
- Day 5：录第一轮素材并找陌生人试玩
- Day 6：按试玩结果只改最伤转化的两刀
- Day 7：输出继续/转向/砍掉结论

这才叫项目管理，不是日程表自嗨。

#### 对多Agent协同
切片阶段最适合多 Agent 的不是“大家一起随便干”，而是按体验节点拆：
- Agent A：主玩法闭环
- Agent B：UI/引导/结算反馈
- Agent C：自动打包/日志/性能监控
- 主脑验收：按 Gate 过关，不按提交数量算功劳

这能避免多 Agent 同时很忙，但谁都没把完整体验做出来的烂局。

---

### 8. 一句话方法论
**Vertical Slice 管理的本质，不是把一小段做漂亮，而是用一小段逼项目说真话：这东西能不能稳定复制、能不能拿去验证、值不值得继续投。**

## 课题：【专家进阶延展】试玩测试运营与反馈闭环管理（Playtest Ops）：别再只“找人试玩”，要把试玩变成版本决策机器

### 0. 为什么把它定为项目管理维度下一个未攻克课题
路线图主课题里的敏捷、Git/CI、MVP边界、协同、风险预警、上线清单、垂直切片都已经补得差不多了，但还有一个独立项目最常见的断层：
**切片做出来了，却不会系统化地找对人测试、收对数据、做对决策。**

这不是“用户研究”那么简单，它本质上是项目管理问题：
- 什么时候测？
- 找谁测？
- 每轮要验证什么？
- 什么问题先修，什么问题先忍，什么方向直接砍？
- 如何把一堆感性反馈压缩成版本去留决策？

所以这次我把项目管理维度的下一个细分课题，定为：
**试玩测试运营与反馈闭环管理（Playtest Ops）**。

---

### 1. 先下结论：试玩不是“收意见”，而是“用最便宜的方式提前暴露错误方向”
很多独立开发者把试玩理解成“发个包给朋友看看”。这做法很烂，原因有三条：
1. 朋友会给面子，反馈失真；
2. 没有预设验证问题，最后只收回来一堆碎意见；
3. 没有分级和决策规则，反馈越多越乱。

真正成熟的 Playtest Ops，不是多跑几轮，而是每一轮都要服务一个明确决策：
- 这个玩法值不值得继续？
- 哪个爽点成立了？
- 哪个卡点是理解问题，哪个是数值问题，哪个是技术问题？
- 下一周该修主链路，还是该直接砍方向？

所以试玩的价值，不是“大家说了什么”，而是：
**这一轮之后，我们敢不敢做更大的投入。**

---

### 2. 2024-2026 的方法论信号：行业已经把试玩从“测试行为”升级成“受控运营流程”

#### 信号A：Steam Playtest 把“低风险外测”产品化了
Steam 官方文档把 Steam Playtest 定义得很明确：它用一个与主游戏关联、但独立的 child appID 来做测试。核心价值不是技术噱头，而是三刀：
- 不用大规模发 key，发放与回收更干净；
- 不影响主商店评价和愿望单节奏；
- 可以按阶段控制测试开放规模。

对项目管理的启发非常直接：
**试玩环境必须和正式发布链路部分解耦。**
你需要的是“能快速扩测、能快速止血”的测试容器，而不是把所有风险压到正式产品页上。

#### 信号B：Games User Research 2023/2024/2026 的连续内容说明，试玩早就不是某个岗位的私活
GUR 的《2023 Playtest Survey》有个很关键的结论：
**试玩是跨职能协作，不只是研究员的事。**
设计、制作、UX、项目管理都会深度卷入，因为最后要一起判断哪些发现值得进入版本计划。

它还强调了一点：很多团队对“playtest”的定义并不统一，但只要是**使用外部玩家来获取证据**，就该按研究和决策流程管理，而不是随手问问。

这说明对独立团队最关键的不是岗位分工，而是：
**每一轮试玩结束后，必须有人把发现翻译成版本行动。**
没有这个翻译环节，试玩就是社交活动。

#### 信号C：远程试玩平台的成熟，逼着团队把“任务、问卷、视频、遥测”一起设计
Games User Research 在远程试玩平台综述里讲得很实：远程平台不是只帮你找人，它们真正值钱的是能把下面几样东西一起回收：
- 玩家操作视频
- 问卷答案
- 行为数据/遥测
- 任务完成情况

并且文章直接提醒：
**不要再拿朋友、同行、开发群互测，真实玩家样本质量高得多。**

这对我们意义很大。因为以后做 7 天垂直切片时，最容易自欺欺人的就是“圈内人都看懂了”。那不算验证，真正有价值的是陌生目标用户能否自己走通。

#### 信号D：问卷本身也已经被视作一门独立技能
GUR 关于 playtest survey 的文章强调，问卷不是“多问几句”，而是要避免诱导、避免空泛，优先验证：
- 玩家是否理解目标
- 玩家是否感到卡顿/挫败
- 玩家是否愿意再来一局
- 玩家如何描述刚刚发生的关键时刻

也就是说：
**问卷不是拿来收夸奖的，是拿来定位理解断点和情绪峰谷的。**

#### 信号E：2026 的平台工具开始把“视频 + 遥测 + 即时报错”打成一套
Microsoft 在 2026 年对 PlayFab Foundation Mode 的介绍里，把 Game Data Stream 明确列成核心能力：可以跨平台生成玩家行为遥测事件，观察玩家与每个功能的交互情况。
Xbox Insider 页面则更进一步，直接强调两件事：
- 玩家提交问题时可附截图与最近 30 秒视频；
- 可以快速部署本地化问卷，并按你控制的规模逐步放量。

这说明现在外测的成熟形态已经不是“靠主观反馈”，而是：
**主观问卷 + 行为遥测 + 报错证据 + 分阶段放量**。

---

### 3. 真正该管理的，不是“玩了没”，而是这一轮试玩要验证哪种决策
以后每轮试玩，先别问“要不要找 10 个人试试”。先问：
**这一轮结束后，我们到底要拍什么板？**

我建议把试玩目标粗暴分成 4 类：

#### A. 理解验证（Comprehension Test）
要验证的问题：
- 玩家 30 秒内看不看得懂目标？
- 第一次失败后，知道自己为什么输吗？
- 会不会把核心按钮、升级或交互完全看漏？

适合阶段：
- 原型初期
- 新手前 1-2 分钟
- 新系统首次接入

#### B. 爽点验证（Delight Test）
要验证的问题：
- 游戏里是否真的出现了“卧槽，这一下有点爽”的瞬间？
- 这个瞬间稳定出现，还是只在设计者心里存在？
- 玩家愿不愿意主动再玩一局去追这个瞬间？

适合阶段：
- 垂直切片
- 核心玩法调优
- 买量素材反向立项

#### C. 阻塞验证（Friction Test）
要验证的问题：
- 卡点是输入、镜头、UI、数值、节奏还是性能？
- 玩家是“不会”，还是“懒得学”，还是“明白但不爽”？

适合阶段：
- 进入外测前
- 留存问题排查
- 广告/付费/结算链路接入后

#### D. 去留验证（Go / Pivot / Kill Test）
要验证的问题：
- 这个切片值不值得继续扩？
- 如果只给 7 天，还值得再投 7 天吗？
- 如果陌生用户都没有明显兴趣，是否应该直接砍掉？

适合阶段：
- 7天垂直切片末尾
- 发行沟通前
- 小额买量前

没有目标分类的试玩，几乎注定会收回无用噪音。

### 4. 适合独立游戏/小团队的试玩运营闭环：一轮只做 7 件事

#### 第一步：写《本轮试玩任务书》
每轮必须只有一个主问题，最多再带两个次问题。
模板：
- 本轮唯一要验证的事：
- 目标用户画像：
- 本轮不关心什么：
- 成功阈值：
- 失败阈值：
- 这轮之后可能做的决定：继续 / 修正 / 砍掉

例子：
- 唯一问题：陌生玩家能否在 90 秒内理解《光与朽》的摆位与激光主爽点？
- 不关心：长期养成、剧情包装、商店UI
- 成功阈值：7/10 玩家能在首局内主动利用一次激光布局优势
- 失败阈值：超过半数玩家把失败归因于“看不懂/不知道该干嘛”

#### 第二步：按目标用户招人，别按你的人脉招人
试玩样本至少分三档：
1. **错样本**：朋友、同行、开发者群——只能拿来查崩溃和明显引导问题；
2. **近样本**：相似玩家，但不是精准目标用户；
3. **真样本**：会真实下载、真实流失、真实付费或真实划走的人。

结论很狠：
**做玩法去留判断时，错样本的夸奖价值极低。**

对我们现在最实用的做法：
- AI 视频反向立项阶段：优先找会刷短视频、会点进小游戏、但不是开发者的人；
- 《光与朽》调优阶段：优先找能接受轻策略/轻塔防、但对规则没耐心的普通玩家；
- 发行合作前：找发行视角的人看“这东西能不能被一句话讲清”。

#### 第三步：每轮固定收三类证据，少一样都容易误判
每轮试玩最低配也要收下面三类东西：
1. **行为证据**：录像、操作路径、停顿点、退出点；
2. **主观证据**：试玩后 3-5 个问题的短问卷；
3. **系统证据**：崩溃、卡顿、关键事件埋点。

只听玩家说，不看行为，会被主观解释骗；
只看埋点，不看表情和语言，会不知道为什么；
只看录像，不看结尾问卷，又会缺少动机和意图信息。

#### 第四步：问卷必须短，而且问题要脏、要准
以后每轮试玩后的问卷，不要写成市场调研废话。建议固定围绕下面 5 问：
1. 你觉得这游戏让你做什么？
2. 你第一次感觉爽/有趣，发生在什么时候？
3. 你第一次迷糊或烦，是在什么地方？
4. 如果再来一局，你第一件会改什么？
5. 你愿不愿意继续玩/推荐/再试一局？为什么？

这 5 问的价值在于：
- 测理解
- 测爽点
- 测摩擦
- 测学习迁移
- 测继续意愿

够狠，够短，也足够驱动决策。

#### 第五步：24小时内做反馈分拣，不让数据烂掉
试玩结束后 24 小时内，必须把发现分进下面 5 桶：
1. **理解问题**：玩家没看懂规则、目标、按钮或反馈；
2. **爽点问题**：会玩了，但不爽、不惊、不想再来；
3. **节奏问题**：太慢、太急、压力点不对、成长点太晚；
4. **技术问题**：崩溃、掉帧、卡死、误触、广告异常；
5. **商业问题**：广告打断位置错、转化文案弱、看完没奖励感。

然后再打优先级：
- P0：阻断试玩或阻断理解
- P1：显著伤害爽点或复玩意愿
- P2：可见瑕疵，但不影响主决策
- Archive：有趣，但当前不处理

#### 第六步：每条反馈都必须翻译成动作，不许停留在“用户说”
错误写法：
- 用户说太难
- 用户说看不懂
- 用户说不够爽

正确写法：
- 5/8 玩家在第 3 波前没有形成有效布局，因此把失败归因为“敌人太快”，疑似问题是前 90 秒可用信息不足。
- 6/10 玩家没注意到强化三选一里的核心标签，说明 UI 层级与首次讲解失败。
- 首次爽点平均出现在 145 秒，超过我们希望的 90 秒目标，需前移一次明显清屏或折射收益反馈。

项目管理里最重要的，不是保存原话，而是把原话压成：
**问题假设 + 证据 + 下一刀改什么。**

#### 第七步：用固定决策门，避免每轮都靠感觉拍脑袋
每轮试玩结束后，只允许进入三种结论之一：
- **继续放大**：核心体验成立，只修关键阻塞；
- **继续但重切**：方向没死，但必须换入口、节奏或表达；
- **停止投入**：爽点不成立，或理解成本过高，不值得继续烧时间。

不要第四种结论：“再看看吧。”
那是项目管理里的慢性自杀。

---

### 5. 2026 年最值钱的升级：把遥测和视频变成“反馈仲裁器”
现在最大的坑，是玩家主观反馈很容易互相打架：
- 有人说太难
- 有人说太简单
- 有人说无聊
- 有人说不知道怎么玩

如果没有证据仲裁，你只会被意见拖着跑。

这时就要靠两类硬证据：

#### A. 事件遥测
至少埋下面 6 个事件：
- 首次进入战斗时间
- 首次爽点触发时间（例如第一次大清屏/连锁）
- 首次升级选择时间
- 首次接近失败/残血时间
- 失败原因或失败波次
- 是否点击复活/双倍奖励

这类数据不能解释全部，但能把“感觉”变成可比较的版本指标。

#### B. 录像/回放
Xbox Insider 把“问题提交时附截图和近 30 秒视频”当核心卖点，这个思路太对了。
因为很多 bug 和挫败，不看最后 20-30 秒根本不知道发生了什么。

对我们这种独立项目，完全没必要一开始就搞复杂平台，但必须保留一种轻量机制：
- 外测者录屏
- 或我们自己要求关键节点录屏
- 或在陌生试玩时屏幕录制 + 口述

一句话：
**主观反馈负责告诉你“他不爽”；录像和遥测负责告诉你“为什么不爽”。**

---

### 6. 适合《光与朽》与 7 天切片的试玩节奏

#### 场景A：《光与朽》现在最该怎么测
别再用“大版本体验好不好”这种废问题。下一轮直接测四件事：
1. 90 秒内是否出现第一次明确爽点；
2. 玩家是否在第 3-5 波前理解摆位价值；
3. 第一次失败后，玩家是否知道该改布局还是改升级；
4. 复活广告是否出现在情绪峰值点，而不是随机打断点。

对应要收的证据：
- 首次爽点秒数
- 首次有效升级选择率
- 首败波次与主观失败原因
- 广告点击率 + 看完后是否继续完成本局

#### 场景B：后续 7 天垂直切片怎么管
以后 7 天切片，试玩不要拖到最后一天才做，应该分两轮：
- **第 3-4 天：理解验证轮** —— 测入口、目标、第一爽点；
- **第 6-7 天：去留验证轮** —— 测再来一局意愿、传播点、是否值得继续投。

这样做的好处是：
你不是在成品前夕才发现方向烂，而是在还来得及砍的时候就狠狠干刀。

#### 场景C：AI 视频反向立项怎么用
如果我们先从视频素材倒推玩法，那试玩的主问题就不该是“这个完整不完整”，而该是：
- 视频里承诺的爽点，进游戏后是否在 60-90 秒内兑现？
- 玩家是否觉得“广告骗我”，还是“卧槽，真差不多”；
- 第一次爽点后是否愿意继续点第二局。

这是项目管理，不是创意自嗨。

### 8. 最该记住的 8 条铁律
1. **每轮试玩只验证一个主问题。**
2. **朋友样本只配查崩溃，不配决定方向。**
3. **录像、问卷、埋点三件套缺一不可。**
4. **问卷只问能驱动决策的问题。**
5. **24小时内必须完成反馈分拣。**
6. **每条反馈都要翻译成可执行动作。**
7. **试玩结论只能是继续、重切或停止。**
8. **如果一轮试玩没有改变你的计划，这轮试玩大概率白做了。**

### 9. 本课题的执行结论
真正高级的项目管理，不是把版本做完后再求人提意见，而是把试玩本身设计成版本决策机器。

以后统一按这句话执行：

**“试玩不是收意见，是用真实玩家的行为、情绪和流失点，替我们提前判死刑或发通行证。”**

对我们当前项目，最值钱的动作不是再加功能，而是立刻把每轮测试写成任务书，固定收录像+短问卷+关键埋点，并在24小时内完成分拣与 go/pivot/kill 决策。

这才是真正能让 7 天切片和《光与朽》少走弯路的项目管理。

## 课题：【专家进阶延展】实验漏斗与立项闸门（Experiment Portfolio + Go/Kill Gates）：如何在多个 7 天切片里快速选赢家

### 0. 为什么把它定为项目管理维度下一个未攻克课题
路线图主课题里的敏捷、MVP 边界、垂直切片、试玩闭环都已经补得很扎实，但我们现在真正要打赢的，不是“把一个项目推进好”，而是：
**如何在多个候选方向里，用最小成本快速筛掉烂方向，把时间和美术火力押到真正可能赚钱的那个。**

这已经不是单项目管理，而是**实验组合管理**。对我们这种要做 AI 视频反向立项、7 天垂直切片、陌生用户测试的小团队来说，不会设闸门，就会掉进两个坑：
1. 同时开太多原型，谁都没跑出结果；
2. 明明负信号已经很明显，却因为“都做到这了”继续烧时间。

所以这节课的核心不是“怎么多做几个原型”，而是：
**怎么把原型池做成一个会自动淘汰弱者、持续抬高赢家权重的立项漏斗。**

---

### 1. 先下结论：别再一个个“喜欢就做”，要把项目候选当投资组合管理
2025-2026 的产品与项目管理共识已经很明确：
* **Stage-Gate 不是老古董**，而是用阶段 + 闸门做 go / hold / kill 决策的低成本治理框架。
* **实验不是靠灵感，而是靠方法**。强团队会接受“负信号连续两周就砍”，而不是硬拖几个季度。
* **小团队不该迷恋复杂评分系统**，而应该用少数几个高改变决策的指标，把方向分出层级。
* **Vertical Slice 的意义不只是展示，而是帮助发行方和团队判断：你是不是挑对了支柱，是否值得继续投入。**

翻译成人话就是：
**我们不是在管理创意，我们是在管理下注。**
每个 7 天切片都不是“作品”，而是一次带预算上限的试投；没过闸，就该死。

---

### 2. 2025-2026 的最新信号，给了我们什么狠结论

#### 信号A：Asana 2025 重新强调 Stage-Gate 的核心价值——每一阶段后都必须做继续、暂停或停止决策
Asana 在 2025 的 Stage-Gate 指南里把这套方法讲得很直白：项目被分成若干阶段，而 gate 不是汇报会，而是**决策检查点**。每个 gate 的工作不是“看起来进展不错”，而是明确判断：
* 继续推进
* 暂停等待
* 直接停止

这对我们最大的提醒是：
**每个实验周结束后，必须给出清晰处置，而不是“再看看”。**
“再看看”不是稳健，是烂管理。

#### 信号B：Product School 2026 的产品趋势判断很狠——强团队会在两周强负信号后果断砍项目
Product School 在 2026 的趋势文章里直接说：
**一个团队在两周强负信号后砍掉项目，是正常的，不是失败。**

这条非常值钱。因为独立开发最容易犯的病，就是把已经投入的时间当成继续投入的理由。实际上，强负信号出现后继续拖，只会把“学习成本”变成“沉没成本雪球”。

#### 信号C：monday 2026 提醒小团队优先用简单框架——Value vs Effort 比大而全评分更适合资源紧的小组
monday 2026 的优先级框架总结提到：
**小团队通常更适合简单方法，比如 Value vs Effort；组织越大，才越需要更复杂的结构化模型。**

这对我们很关键。我们不需要搞十几列打分表把自己累死。真正在用的，应该是：
* 价值信号够不够强
* 成本会不会拖爆
* 证据可信不可信

简单，但必须狠。

#### 信号D：Playstack / devcom 2025 的 Vertical Slice 分享，核心不是“更精致”，而是“是否选对了游戏支柱”
Playstack 在 2025 devcom 的 vertical slice 议题里明确强调：
他们评估过大量 vertical slices，最重要的不是堆内容，而是：
* 是否抓住正确的核心支柱
* 是否挑了最能代表项目价值的内容
* 是否避免了常见误区
* 是否呈现得足够清晰、足够能打动决策者

这说明切片不是美术样片比赛，而是**支柱选择能力考试**。
如果支柱选错， polish 越多，死得越贵。

#### 信号E：Aakash 2026 的管理建议非常适合我们——重大 greenlight 前至少盯四类信号：adoption、retention、quality、business
Aakash 在 2026 的管理文章里给了一个很硬的判断：
在 greenlight 重大变化前，他通常至少要看：
* 一个 adoption signal
* 一个 retention signal
* 一个 quality signal
* 一个 business signal

这几乎可以直接抄到我们的实验漏斗里。因为原型是否继续，不该只看“我觉得挺爽”，而要看：
1. 有没有人愿意点进来；
2. 玩了后愿不愿意再来一局；
3. 体验是不是稳定不崩；
4. 这东西有没有传播、买量、合作或变现可能。

#### 信号F：monday 2026 在 PPM 场景里强调 scenario planning——先做 what-if 沙盘，再决定火力分配
monday 2026 的项目组合管理材料提到：
**scenario planning 的价值，是先在沙盘里做“如果把资源挪给 A/B/C，会发生什么”的推演。**

对我们意味着：
**不要等原型全做出来再比，应该先在纸面就淘汰一批。**
如果一个方向即使通过也很难产出可投素材、很难形成 IAA 验证、很难做 7 天切片，那它在立项前就该被降权。

---

### 3. 真正适合我们的不是“大公司组合管理”，而是“三层漏斗 + 四信号闸门”

我建议以后所有候选项目统一走下面这套漏斗。

#### 第一层：素材与题材闸门（Signal Gate）
先问的不是“这个游戏完整不完整”，而是：
**市场会不会先给你一个点进来的机会。**

来源可以是：
* 抖音/小红书/B站/TikTok 的素材信号
* 评论区“想玩 / 游戏名 / 哪里下载”的真实需求
* 竞品买量素材的可复制动词
* 我们自己做的 AI 视频承诺是否够强

这一层的通过标准，不是证明游戏好玩，而是证明：
**它有被陌生人注意到的潜力。**

不过闸的典型死法：
* 题材弱，钩子不成立
* 视觉动词不清
* 视频承诺无法一句话讲清
* 素材只能靠解释，不能靠直觉传播

#### 第二层：7 天垂直切片闸门（Slice Gate）
过了素材闸，才配进入 7 天切片。
这一层验证的是：
**承诺能不能在一个极小但完整的体验里兑现。**

最低要回答四个问题：
1. 90 秒内能否理解目标？
2. 120 秒内能否出现第一次明显爽点？
3. 失败后玩家知不知道下一把该改什么？
4. 能不能录出 3 条可传播素材？

如果这四条里两条都站不住，方向基本就该砍，不要恋战。

#### 第三层：试玩与商业化闸门（Validation Gate）
切片过了，还不代表能投。
第三层要验证的是：
**这个方向不只“能玩”，而且“能被陌生用户接受，并有商业化延展可能”。**

重点看四类信号：
* **Adoption**：素材点击、试玩愿望、愿不愿意进下一步
* **Retention**：是否主动再开一局、是否愿意继续试玩
* **Quality**：是否存在理解阻断、崩溃、卡顿、误触、节奏断裂
* **Business**：是否能形成可投素材、可讲清卖点、可接发行/合作/IAA 验证

只有第三层过闸，才配进入更重的开发、买量或合作沟通。

---

### 4. 一套能真正落地的“实验组合评分卡”
别搞复杂。我建议每个候选方向只打 6 个分数，每项 1-5 分：

1. **钩子强度**：3 秒内能不能让人停下来看
2. **承诺兑现**：视频或一句话承诺，进游戏后 60-120 秒能不能兑现
3. **复玩冲动**：失败或结算后，玩家会不会立刻想再来一局
4. **实现效率**：7 天内能不能做出可测切片
5. **商业适配**：是否适合 IAA、素材投放、发行沟通或社媒传播
6. **扩展潜力**：如果成立，能否自然扩成 30 天产品，而不是一次性 gimmick

然后再加一个否决项：
**是否存在致命阻断？**
例如：
* 玩法太吃解释
* 真机表现撑不住
* 没法在小团队产能里复制
* 核心爽点只能靠精致内容堆出来

有致命阻断，前面打分再高也先停。

---

### 5. Stage-Gate 不要做成文书工作，要做成“砍项目开关”
以后每个候选方向，统一走下面 4 个 gate：

#### Gate 0：纸面预审（半天内）
只看：
* 钩子是否清晰
* 是否符合当前 90 天主线
* 是否能在 7 天内做出最小切片
* 是否有可验证的 IAA / 传播 / 发行意义

结论只能三种：进 / 缓 / 否。

#### Gate 1：第 3 天中期审判
检查：
* 主交互骨架是否已跑通
* 首个爽点是否已出现雏形
* 方向是否仍符合最初承诺

若第 3 天还没有主爽点原型，就高度危险。不要等第 7 天再认输。

#### Gate 2：第 7 天切片审判
检查：
* 是否可给陌生用户试玩
* 是否有 3 条可录制素材
* 是否能用一句话讲清价值
* 是否值得再投 7 天

若回答含糊，默认不进下一阶段。

#### Gate 3：试玩后 greenlight
检查四信号：
* adoption
* retention
* quality
* business

建议规则：
* **四项里至少三项过线** → 继续投入
* **两项过线、一项模糊、一项差** → 允许 pivot 一次
* **两项及以上明显不达标** → kill

这样才叫闸门，不是礼貌性复盘。

---

### 6. 最适合我们的资源分配规则：赢家吃资源，输家进坟场
独立团队最怕平均主义。方向一多，最蠢的做法就是每个都留一点火。

我建议直接执行下面 5 条：
1. **同时在跑的高优先实验不超过 3 个**。
2. **每个新实验启动，必须说明要替代或挤掉谁的资源。**
3. **周复盘时只允许一个方向升仓。**
4. **被 kill 的方向进入“点子坟场”，保留 kill 原因，不准偷偷复活。**
5. **除非出现新证据，否则 14 天内不重新讨论已 kill 项。**

这样做的价值不是冷酷，而是防止我们被“都挺有意思”这类废话拖死。

---

### 7. 对《光与朽》与后续 AI 视频反向立项的直接应用

#### 对《光与朽》
《光与朽》现在已经不是“再多做功能”的阶段，而是要重新判断：
**哪些体验支柱还值得继续加码，哪些只是历史包袱。**

用这套漏斗去看，接下来最该优先验证的是：
* 激光折射翻盘是不是传播级爽点
* 布局失误 → 重开学习链条是否足够清晰
* 广告复活与双倍结算是否刚好踩中情绪点
* 能不能切出真正可投放、可陌生人理解的短素材

只要这些核心支柱证据弱，就别在外围包装上继续烧。

#### 对后续 7 天切片
以后做新方向，不准再“这个也顺手试试”。
统一按下面流程：
1. 先做素材/题材预审；
2. 过闸再给 7 天；
3. 第 3 天必须出爽点原型；
4. 第 7 天必须出陌生人可测切片；
5. 试玩后只允许 go / pivot / kill。

这会极大降低“做着做着舍不得砍”的概率。

#### 对多 Agent 协同
组合管理阶段最适合 Agent 做的，不是替我们拍板，而是：
* 并行搜集题材与素材信号
* 生成候选切片任务书
* 帮我们做评分卡与证据整理
* 在 gate 节点汇总 adoption / retention / quality / business 四类证据

拍板权必须留在人类主脑这里，因为 gate 的本质是**下注裁决**，不是文档整理。

## 课题：【专家进阶延展】项目组合管理与资源配置（Portfolio Management for Solo/Small Game Studio）：不是把项目都推进，而是把资源砸向最可能赢的那一个

### 1. 为什么它是当前“下一个未攻克课题”
`five_dimensions_expert_roadmap.md` 里项目管理维度的四个主课题——极简敏捷、Git/CI、MVP边界、外包/多Agent协同——都已覆盖。结合既有学习记录，当前最缺的不是“如何把单个任务做完”，而是：

**当我们同时面对《光与朽》复盘、下一款7天垂直切片、AI视频反向立项、内容实验时，如何决定谁该拿时间、谁该被砍、谁只配拿最低维持资源。**

这就是项目组合管理（Portfolio Management）的核心：
- 不再问“这个任务值不值得做”；
- 而是问“在有限时间/现金/注意力下，哪个方向最值得继续活下去”。

对独立游戏团队尤其关键，因为我们真正稀缺的不是创意，而是：
1. 主人的连续专注时间
2. 可承受试错次数
3. 能进入下一轮验证的现金流与认知带宽

### 2. 一句话定义：项目组合管理是什么
传统项目管理管的是**把单个项目做稳**；项目组合管理管的是**选对项目、配对资源、及时止损**。

换成我们的语境：
- **项目管理**：把《光与朽》某个版本按时做出来。
- **项目组合管理**：在《光与朽》优化、下一款切片、视频素材测试、平台验证之间，决定本周的70%火力该打哪一个。

Atlassian 与 Aha 的方法论里反复强调同一个点：组合管理本质是**战略对齐 + 优先级排序 + 资源配置 + 持续复盘**。不是做一张漂亮路线图，而是持续回答：
- 这项工作服务哪个业务目标？
- 如果不做，会失去什么？
- 如果继续做，会吞掉什么？
- 当前最稀缺资源究竟是时间、钱、技术，还是认知焦点？

### 3. 对独立游戏最实用的组合管理框架：四层漏斗

#### 第一层：方向池（Idea Pool）
所有方向都能进池，但只记录一页卡片，不准一上来就重投入。

每个方向卡只写8项：
1. 方向名
2. 一句话承诺（玩家/市场到底买什么）
3. 目标平台
4. 目标人群
5. 关键钩子
6. 要验证的最大风险
7. 最小实验方式
8. 下一次评审日期

**规则**：没有“最大风险”定义的方向，不许立项。

#### 第二层：证据门（Evidence Gate）
任何方向必须先过最小证据门，才能吃到更多资源。

证据优先级：
1. **真实用户行为**（点进、看完、试玩、复玩、付费/看广告）
2. **陌生人反馈**
3. **平台冷数据**（CTR、完播、留资、愿望单、次留）
4. **团队主观判断**

狠规则：**主观热爱不能替代市场证据。**
喜欢一个点子，不等于它配得上7天以上开发资源。

#### 第三层：资源阀门（Funding Gate）
资源按阶段释放，而不是一次性承诺。

推荐三档：
- **0级探索**：2~4小时；只允许做命题、搜竞品、做素材草图、写验证问题。
- **1级切片**：3~7天；只允许做一个能拿到真实反馈的垂直切片/视频实验。
- **2级加码**：2~4周；仅给已经出现强信号的方向，补玩法深度、留存结构、商业化初版。

任何方向都必须从低档往上爬，**禁止跳级重仓**。

#### 第四层：Go / Hold / Kill 决策门
每次评审只允许四种动作：
- **Go**：继续加码
- **Hold**：暂缓，但保留资产
- **Kill**：停止投入，只归档经验
- **Pivot**：核心命题不变，但验证方式或平台表达改掉

最蠢的死法就是第五种隐形状态：**“先放着，但团队还在偷偷投入”**。

### 4. 一套适合我们的小团队评分板：别搞复杂，够狠就行

推荐使用 6 维评分，每项 1~5 分，总分 30 分：

1. **市场钩子强度**：3秒内能不能说清，能不能做成视频首屏。
2. **验证成本**：拿到第一轮真实证据要花多大代价。
3. **复用度**：代码、素材、机制、数据能否迁移到后续项目。
4. **商业潜力**：IAA/IAP/发行合作/平台匹配度是否清晰。
5. **执行胜率**：我们当前能力和资源能否在短周期内做出像样版本。
6. **学习价值**：即便失败，是否也能产出高价值认知资产。

### 5. 推荐的决策公式：先看赔率，再看成本
单人团队不适合照搬大公司繁琐财务模型，最实用的是：

**Priority Score = (市场信号 × 商业潜力 × 执行胜率) ÷ 验证成本**

解释：
- 市场信号弱，再酷也别上头；
- 商业路径不清，再热闹也只是爱好；
- 执行胜率太低，再大市场也是幻觉；
- 验证成本太高，会拖死节奏。

如果两个方向分数接近，优先：
1. 复用资产更多的；
2. 更快拿到陌生人反馈的；
3. 更能服务公司长期护城河的。

### 6. 最新案例与行业启发

#### 案例1：Lund University / ICSOB 2024（2025发表）——独立游戏的实验，本质上是“低数据、低样本、重定性”的决策科学
Linåker 等人在 2025 发表的《Pre-release experimentation in indie game development: an interview survey》中，访谈了 10 家独立游戏开发者，结论很硬：
- 预发布实验是必要动作；
- 但 indie 团队在早期几乎拿不到足够大的用户数据；
- 因此真正可用的不是大而全统计学，而是**小样本、高质量、强问题导向**的实验设计；
- 早期实验更多依赖**定性反馈 + 有限行为数据**的联合判断。

对我们的意义：
- 不要等“样本足够大”才做决策，那会把窗口期等没；
- 要先设计“这一轮只验证一个最大风险”；
- 样本少时，重点不是求精确结论，而是排除明显错误方向。

#### 案例2：IMPRESS（2025）——《The Ouroboros King》早期愿望单长期低迷，后续靠精准传播扭转
IMPRESS 在 2025 的 indie 营销案例总结里提到，《The Ouroboros King》前约 10 个月 Steam 页面仅积累约 500 个愿望单，说明“认真开发”本身不会自动转化为市场势能。后续扭转，靠的不是继续闷头做，而是**更精准的传播对象与内容表达调整**。

对组合管理的启发：
- 某个方向没起量，问题未必是产品本体，也可能是“市场表达方式错了”；
- 所以 Kill 前要先区分：
  1. 核心乐趣不成立；
  2. 传播钩子不成立；
  3. 渠道与受众没打准。
- 这意味着组合管理里必须给“表达实验”保留一格资源，不能所有失败都归因于玩法。

#### 案例3：Mordor Intelligence（2026）——独立市场越来越依赖“作品组合”和长尾回收，不是只赌单款爆发
2026 市场报告提到：Devolver Digital 2024 年收入约 1.048 亿美元，其中 **88% 来自旧作目录**；Team17 某阶段收入中 **92% 来自目录产品**。这说明成熟发行方靠的不是单款梭哈，而是**组合回收 + 长尾积累**。

对我们很重要：
- 单项目思维会让你把每个原型都当生死战；
- 组合思维会让你把每个切片当“资产试验田”；
- 真正值钱的是：哪怕项目被 Kill，也留下可复用素材、玩法模块、买量洞察、受众画像、平台反馈。

也就是说，**失败项目不是零，只要它产出可迁移资产。**

### 7. 独立游戏最容易犯的 6 个组合管理错误
1. **平均用力**：每个方向都推进一点，结果没有一个形成突破。
2. **证据和投入脱钩**：零证据就重投入；有证据的方向反而缺资源。
3. **只看完成度，不看验证价值**：做了很多内容，但没减少核心不确定性。
4. **不肯 Kill**：因为舍不得已投入成本，继续烧未来时间。
5. **把“我喜欢”当“市场会买”**：这是最常见的自我欺骗。
6. **没有资产沉淀机制**：项目死了，经验也跟着死。

### 8. 给我们现在最适合的执行制度：每周一次组合评审，30分钟砍刀会

#### 会议名称：周组合评审（Portfolio Review）
频率：每周一次，30分钟，必须出结论。

#### 固定议程
1. **看方向板**：当前有哪些活项目/候选方向？
2. **看证据**：上周新增了什么真实信号？
3. **看资源**：下周主人 70% 的主火力投给谁？
4. **做动作**：每个方向必须是 Go / Hold / Kill / Pivot 之一。

#### 输出物
每个方向一张状态卡：
- 当前阶段
- 本周新增证据
- 核心风险是否下降
- 下周资源级别
- 决策动作

### 9. 针对 GamePlanningDoc 的落地建议：建立“三轨组合”而不是“一锅乱炖”

#### 轨道A：现金流/复盘轨
目标：从《光与朽》《美妆叠叠乐》的真实数据里榨出复用认知。
资源建议：**20%**
只做：
- 留存/IAA/广告点位复盘
- 失败原因拆解
- 可复用代码与发行资产整理

#### 轨道B：高潜实验轨
目标：筛出下一款 7 天垂直切片候选。
资源建议：**60%**
只做：
- 题材×玩法钩子组合
- AI视频反向立项
- 陌生人测试
- 短视频CTR/完播验证

#### 轨道C：品牌与分发轨
目标：建立内容信号与后续发行蓄水。
资源建议：**20%**
只做：
- Douyin/小红书/B站内容信号测试
- 开发过程展示
- 钩子包装验证

### 10. 资源分配硬规则：没有信号，不准升档
- 没有真实点击/完播/试玩证据 → 不准从0级探索升到1级切片
- 没有复玩/留存/口头推荐信号 → 不准从1级切片升到2级加码
- 没有清晰商业路径 → 不准承诺大体量生产

### 11. 最关键的一句狠话
**项目组合管理不是“多项目并行”，而是“持续剥夺弱方向的资源，把火力集中到正在冒烟的那一个”。**

### 12. 本课题对我们当前项目的直接应用
对主人现在的阶段，最该做的不是再开更多坑，而是立刻建立下面这个判断顺序：
1. 《光与朽》只保留“复盘价值”和“可迁移资产提炼”，别继续情绪化加内容；
2. 下一款候选只允许同时跑 2~3 个切片方向，不能超过这个上限；
3. 每个切片先验证视频钩子，再决定要不要做试玩版；
4. 任何方向连续两轮无强信号，直接 Hold 或 Kill；
5. 每周固定做一次组合评审，强迫自己把时间重新分配。
