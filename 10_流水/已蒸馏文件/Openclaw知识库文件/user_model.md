## 稳定习惯与偏好

### 1. 工作方式偏好
- **先把核心玩法/功能跑通，再补特效与精修**。接受“先用临时特效代替，后续再替换正式资源”的推进方式。
- **强烈偏好模块化拆分**：会把理财、IP、主脑开发、美术学习等任务分频道/分上下文隔离，避免主脑上下文污染、限速和任务串味。
- **偏好“关键进展跨频道同步，细分工作单频道沉淀”**：重要里程碑会同步到多个相关频道，但日常执行仍保持分域管理。
- **偏好“内容/知识资产化”**：要求把可复用输出沉淀到知识库、项目文档或固定目录，而不是只停留在聊天记录里。
- **习惯以结果为导向推进**：更在意“能不能落地”“玩家是否一眼看懂”“开发成本是否可控”，而不是空泛创意。
- **偏好低风险高收益方案**：尤其在《光与朽》上线冲刺期，优先选择复用现有框架、开发成本低、体验提升大的设计。

### 2. 游戏开发偏好
- **极度重视玩家体验的清晰度**：反复否决“看不懂、反馈冲突、体验恶心”的机制设计。
- **偏好视觉与机制强绑定**：怪物外观必须一眼传达机制，不接受“看起来像A，实际是B”的设计含糊。
- **坚持纯2D俯视视角约束**：所有法阵、挂件、特效、怪物结构都必须服从这个视角，不接受透视错乱方案。
- **坚持流体怪物底层设定**：即使到了极寒章节，也要求保住流体特性，而不是变成纯硬质冰块。
- **重视手机端辨识度**：眼睛、情绪表达、轮廓和配色必须在小屏幕上依然清楚。
- **美术风格上倾向“极简2D矢量主体 + 强反馈特效”**，反对厚涂、复杂但不清晰的表现。

### 3. 协作与沟通偏好
- **喜欢直接判断，不喜欢摇摆**：经常要求明确选方案A/B/第三种，不喜欢模糊的“都可以”。
- **对“没回复、漏回复”高度敏感**：一旦工具执行后没有文字回应，会立刻追问，说明“执行后必须明确汇报结果”是硬需求。
- **喜欢先给建议，再直接给可复制落地物**：如 AI 提示词、色号、机制结论、文案模板、频道迁移方案。
- **喜欢“结果 + 存档 + 提交”三连闭环**：很多任务不止要求回答，还要求写入文件、保存到指定目录、必要时提交 Git。
- **对专业性要求高**：会主动指出机制冲突、视觉冲突、透视问题、UI可读性问题，说明其审美和产品判断标准都不低。

## 常用操作模式
- 在 Discord 中通过 **@提问 + 追问细节** 的方式推进任务。
- 会在关键节点直接发送 **阶段完成清单**，让系统基于实际进度切换策略。
- 会把同一个关键进展同步到多个相关频道，兼顾“主脑掌握全局”和“专属频道沉淀记录”。
- 经常要求：
  - 设计怪物/Boss机制与美术提示词
  - 评估多个方案优劣并做取舍
  - 生成小红书/抖音/B站/公众号内容模板
  - 将任务迁移到独立频道或独立 Cron，减少上下文污染
  - 将产出写入文档、知识库，必要时提交 Git
  - 按频道职能长期运营：把某个频道固定成理财、美术、个人IP等专属工作域

## 禁忌
- 讨厌模糊不清、不能落地的建议。
- 讨厌工具执行后不回复、卡住、吞消息。
- 不喜欢高成本但体验收益不明确的机制方案。
- 不接受会与现有视觉语言/技能反馈冲突的设计。
- 拒绝未经审核和随意执行的破坏性操作。

## 长期目标
- **把《光与朽》做出来并成功上线**，这是当前阶段最核心目标。
- 在做游戏的同时，打造“真实独立开发者”个人IP，形成小红书/抖音/B站/公众号联动内容矩阵。
- 逐步建立自己的游戏公司与长期产品线。
- 积累复用的代码模板、创意库、知识库与内容资产库。

## 之后默认优化方向
- 默认继续采用 **分频道、分任务域、分Cron** 的隔离策略。
- 遇到关键里程碑时，默认考虑是否需要 **主频道 + 对应职能频道** 双重同步，保持全局可见与专域归档同时成立。
- 默认在每次工具执行后做**简短明确汇报**，避免“执行了但没回”的体验雷点。
- 默认把高价值输出**同步沉淀到知识库/项目文档**；若任务语境明确，再继续推进到 Git 提交层。
- 默认优先产出 **短结论版 + 可复用模板版**，让主人可以先秒懂，再按需展开。
- 在游戏设计建议中，优先提供：
  1. 成本最低的落地方案
  2. 玩家体验最清晰的方案
  3. 可直接复制的提示词/参数/文案
  4. 能直接回扣《光与朽》当前上线目标的应用建议
