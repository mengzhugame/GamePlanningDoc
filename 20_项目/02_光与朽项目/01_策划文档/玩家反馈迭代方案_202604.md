# 《光与朽》微信小游戏上线反馈分析 & 迭代方案

## Context（背景）
2026-04-20 游戏已上线微信小游戏平台。朋友圈和游戏同行给出了 15 条反馈（见 `Docs/光与朽玩家反馈问题.txt`），覆盖数值、系统、美术、UI 四大类。用户需要先判断"是否该 2 天内紧急修补"，再决定如何进入下一版本迭代。

---

## 问题 1：是否该 2 天内紧急修补？

### ✅ 用户决定：**等 3 天留存数据再决定**（2026-04-20 敲定）

理由如下：

| 维度 | 紧急修补（2 天打包） | 等待 3 天留存（推荐） |
|---|---|---|
| **信号可信度** | 主要是熟人+同行反馈（样本小、带情感偏见） | 真实用户数据（样本大、客观） |
| **研发性价比** | 赶工修 Bug 往往引入新 Bug，且无法在 3 天内重塑留存曲线（那批用户已经被当前版本"劝退"了） | 用数据判定是"体验问题"还是"赛道问题" |
| **核心风险** | Feedback #9（发行警告留存会很差）若属实，紧急修补无法救，反而浪费工期 | 若留存差 → 考虑转 IAA + 接广告 + 进入下一款，止损最优；若留存 OK → 按本文档的 P0/P1 优先级做下一版本 |
| **微信小游戏特性** | 审核+替换包体有摩擦，匆忙修补大概率命中审核延迟 | 顺势把下一版本做扎实 |

### 决策建议：
1. **这 3 天**：不要动代码主干。可以做 **"零风险"的无代码准备**——重看反馈、整理下一版本的 P0 清单（本文档下方已整理）、跑 BattleStatistics 采集新一批数据。
2. **第 4 天拿到留存数据后**：
   - **次日留存 < 20% / 3日留存 < 8%**：留存赛道失败。不要修补——接 IAA 广告（看广告拿体力/图纸 + 复活已有），放置"长尾回本"，团队进入下款立项期。
   - **次日留存 20–35% / 3日 8–15%**：有救但不算爆款。按下述 P0+P1 迭代，目标是第二个版本把留存翻倍。
   - **次日留存 > 35% / 3日 > 15%**：玩法被验证了。按 P0+P1+P2 完整做，重点放在"让喜欢的人更喜欢"（深度化 + IAA 变现点）。

> **关键洞察**：Feedback #9 说"前期无任何让玩家想看广告的计费点"——这是 IAA 小游戏的命门。**即使留存好，也必须在下一版本把"体力/图纸付费点"往前提**，否则留下来的玩家也变现不了。

## 问题 2：下一版本迭代方案（按优先级排序）

> 原则：**先救留存（前 3 分钟体验）→ 再救爽感（核心循环）→ 最后抛光**。
> 每条都标注了对应的反馈编号、涉及文件、改动成本（★低 / ★★中 / ★★★高）。

### 🔥 P0 - 前 3 分钟体验（直接关联留存，必须做）

#### P0-1. 新增"6 波新手引导关卡"做 A/B 测试（反馈 #9，★★）⚠️ 不动主关卡
- **现状**（用户 2026-04-20 再次澄清）：
  - 每关 10 波（9 小怪+1BOSS），总时长约 10 分钟
  - **9 波内有 17 次技能升级（三选一）**——不是 3 次，频率已经很密集
  - 开发者自测"节奏可以"；**BOSS 血量不能下调**（下调后强力 Build 秒 BOSS，毫无 BOSS 体验）
- **❌ 否决方案**：
  - 简单砍波次：17 次升级压进 5 波 → 频率过密，玩家决策疲劳
  - 降 BOSS 血：破坏 BOSS 体验，违反**核心设计原则 1**（爽感不能牺牲挑战性）
- **质疑**：反馈 #9 可能是**主观感受偏差**（有人觉得 10 分钟太长，有人觉得刚好）→ 不能仅凭一条反馈动主关卡
- **✅ 折中方案（用户敲定）**：
  - **保留主关卡 10 波 10 分钟不动**
  - **新增一个"简单版新手引导关卡"**：
    - 6 波（5 小怪 + 1 简化版 BOSS）
    - 预计 3–4 分钟通关
    - 技能升级次数压缩至 **8–10 次**（保持选择节奏不过密）
    - 首次通关后强制回主界面，展示养成入口
  - **作为 A/B 测试入口**：部分新玩家走新引导关卡，部分走原关卡，**对比次留/3留数据**
  - 如果新关卡留存明显更高 → 切为默认；否则回退
- **涉及文件**：
  - 新增 `Ch0_Tutorial` 章节 SO（基于现有 `ChapterConfig.cs` 复制裁剪）
  - 对应的简化版 `WaveConfig` SO
  - 入口分流逻辑（可能在 `GameManager` 或存档系统）
- **改动成本**：★★（复用现有章节/波次架构，主要是配置 + 入口分流）
- **数据验证**：BattleStatistics 需新增"玩家走 Ch0 还是 Ch1"的分流标记

#### P0-2. 护盾 / 血量 UI 新手引导标识（反馈 #8，★）
- **问题**：玩家分不清左边是护盾、右边是血量
- **方案**：首次进入战斗时，HUDPanel 左右两条显示 Tooltip："🛡护盾（优先承伤）"、"❤血量（见底即死）"，2 秒后淡出，只显示一次（存 PlayerPrefs 标记）
- **涉及文件**：`Assets/Scripts/UI/Panels/HUDPanel.cs`
- **改动成本**：★

#### P0-3. 复活后护盾冲击波 + 短暂无敌（反馈 #3，★★）
- **问题**：付费/看广告复活后直接被怪物淹没，复活形同虚设 → 打击付费意愿
- **❌ 原方案（被用户否决）**：屏幕清屏。原因：过于强力，破坏挑战性（违反**核心设计原则 1**）
- **✅ 修订方案**（用户 2026-04-20 指定）：
  1. **复用工程内已有的护盾冲击波效果**（ShieldController 内应已实现冲击波逻辑）
  2. 冲击波作用：**小怪即死** / **大怪（精英/BOSS）被推开一段距离**，但不死
  3. `TurretController` 进入 2 秒无敌状态（视觉上加护盾光环）
- **实施步骤**：
  1. 先定位工程中已有的护盾冲击波实现（`Assets/Scripts/Logic/Player/ShieldController.cs` 或相关）
  2. 在 `RevivePanel.RevivePlayer()` 中触发一次满威力冲击波
  3. 冲击波需要按敌人类型分层处理（小怪死 / 大怪推）
- **涉及文件**：`Assets/Scripts/UI/Panels/RevivePanel.cs`、`Assets/Scripts/Logic/Player/ShieldController.cs`（复用）、`Assets/Scripts/Logic/Player/TurretController.cs`（无敌）
- **改动成本**：★★（复用已有冲击波，主要是串联触发逻辑）

#### P0-4. 熔浆液不再堵死炮口（反馈 #2，★★）
- **问题**：LavaProjectile 物理阻挡激光，贴脸后玩家只能等死
- **方案**：三选一（推荐方案 A）
  - **A. 贴近水晶塔时自动消散**：LavaProjectile 距离塔 < 2m 时自毁并扣一次伤害（给反馈但不阻塞视野）
  - B. 激光命中熔浆液可摧毁它（增加激光穿透/蒸发判定）
  - C. 熔浆液只落在中远距离，不贴脸生成
- **涉及文件**：`Assets/Scripts/Logic/Enemy/LavaProjectile.cs`、`Assets/Scripts/Logic/Enemy/LavaGunnerAI.cs`
- **改动成本**：★★

#### P0-5. 第一波加入"技能流派引导"（反馈 #11 根因分析，★★）⭐ 关键留存抓手
- **深层洞察**（用户 2026-04-20 提出）：反馈 #11"不够爽"可能不是技能本身弱，而是：
  > 玩家不知道该点什么技能，随便点 → 技能之间没有协同 → Build 没成型 → 感觉不爽
- **方案**：
  - 在第一次技能三选一时，弹出"**流派引导**"弹窗，介绍 3 条主流构筑方向（示例）：
    1. **闪电流**（连锁反应 + 闪电球 + 链式伤害）
    2. **穿透流**（折射 + 分裂 + 激光长度）
    3. **爆发流**（暴击 + 伤害加成 + 过载）
  - 玩家选择一个流派后，后续三选一按此流派的核心技能**加权出现**（不是强制只出这一流派，而是概率偏向，保留 Roguelike 随机性）
  - UI 上在 HUD 角落小图标提示当前流派
- **目的**：让新手也能在前期构筑出有协同的 Build → 真正体验到"激光割草"的爽感 → 留存提升
- **涉及文件**：技能选择 UI 面板、`SkillDatabase.cs`（加流派标签）、技能三选一权重逻辑
- **改动成本**：★★（UI + 权重逻辑，但不改核心技能）

#### P0-6. 连锁反应技能描述文字修正（反馈 #5，★）
- **代码真相（已验证）**：`ChainLightningManager.cs:497` 公式为 `baseDamage * (1-0.2)^bounceIndex`，即**每跳衰减 20%**（0.8→0.64→0.51…），不是"衰减至20%"。
- **问题**：当前 Tooltip 文案与实际逻辑的口语化理解有歧义
- **方案**：把技能描述改为精准表述："闪电传递至最多 N 个目标，**每次跳跃后伤害降低 20%**"（或附上第2、3跳的实际百分比示例）
- **涉及文件**：技能描述文本位于 `Assets/Scripts/Data/SO/SkillDatabase.cs` 或本地化文本表
- **改动成本**：★（纯文案）

### ⚔️ P1 - 核心爽感（留存若 OK，必做）

#### P1-1. 自动索敌 + 作为付费点（反馈 #14、#15，★★★）
- **问题**：纯手动瞄准消耗玩家精力，长关卡容易疲劳；反馈明确提议"自动索敌作为付费点"
- **方案**：
  - `TurretController` 新增"自动瞄准"模式（扫描最近/血量最低敌人，平滑转向）
  - **付费/解锁策略**：
    - 免费：每局前 30 秒免费自动瞄准（让玩家尝到甜头）
    - 付费点：看广告解锁本局"全程自动瞄准"，或图纸永久解锁"自动瞄准套件"
  - 体感上应保留手动微调可能（auto-aim 作为辅助，而非替代）
- **涉及文件**：`Assets/Scripts/Logic/Player/TurretController.cs`、`Assets/Scripts/Logic/Player/LaserController.cs`、UI 解锁面板
- **改动成本**：★★★

#### P1-2. 激光长度可感知地变长（反馈 #15，★）
- **当前**：`GameSettings.maxLaserLength = 15f`，有 `MAIN_LASER_LENGTH_CAP`（激光长度上限系统已做）
- **方案**：
  - 基础 `maxLaserLength` 15f → **20f**（提升 33% 视觉爽感）
  - Reflex 技能加成曲线整体上调
  - 注意：要同时校准 `MAIN_LASER_LENGTH_CAP`，否则顶到天花板
- **涉及文件**：`Assets/Scripts/Data/SO/GameSettings.cs`、`Assets/Scripts/Logic/Player/LaserController.cs`
- **改动成本**：★

#### P1-3. 大招改造（反馈 #3、#15，★★★）⚠️ 需小心设计
- **问题**：当前大招系统是"可升级技能"形式，无一次性释放的爆发感
- **❌ 用户否决"一键清屏"**：担心精英怪、BOSS 怎么办？会让挑战玩家无聊——违反**核心设计原则 1**
- **✅ 分层爆发方案（修订）**：
  - 大招释放时的效果**按敌人类型分层**：
    | 敌人类型 | 大招效果 |
    |---|---|
    | 普通小怪 | 即死（清屏体验保留） |
    | 精英怪（熔浆液/炮手/坦克） | **扣 50% 血 + 2 秒眩晕** |
    | BOSS | **扣 8%–12% 血 + 击退** |
  - **限制使用频率**：蓄力条满才能释放（击杀积累 + 看广告充满）
  - 保留"按一下屏幕炸了"的视觉爽感，但不破坏精英/BOSS 的挑战性
  - 复用现有 ChainLightningManager 视觉资源做爆发特效
- **涉及文件**：`Assets/Scripts/Logic/Player/SkillEffectManager.cs`、新增 `UltimateController.cs`、`HUDPanel.cs`（蓄力条UI）、`EnemyBlob.cs`（分层伤害判定）
- **改动成本**：★★★
- **替代方案**（如果"大招"改造风险大）：**不做新大招**，只在 P0-3 复活场景复用护盾冲击波作为"救急清场"

#### P1-4. 弹球怪下落速度加快（反馈 #7，★）
- **问题**：弹得太高、落得太慢 → 等待无聊
- **方案**：
  - 弹球怪 `EnemyData.mass` 上调（加速重力），或 `Rigidbody2D.gravityScale` 提高 50%
  - 或降低最大弹跳速度上限
- **涉及文件**：对应弹球怪的 `EnemyData` SO
- **改动成本**：★

#### P1-5. 击杀怪有概率生成闪电球（反馈 #13，★★）
- **问题**：主角技能单调，不够割草（反馈 #11）
- **方案**：
  - 新增"闪电球"技能/词条：击杀怪有 X% 概率生成一个滞留 3 秒的闪电球，对周围 2m 内敌人每 0.5 秒激光传导一次
  - 复用 ChainLightningManager 的传导逻辑和美术
- **涉及文件**：`Assets/Scripts/Logic/Player/ChainLightningManager.cs`、`SkillEffectManager.cs`、新增 Pooling 条目
- **改动成本**：★★

## 关键原则复盘（写给执行时的自己）

### 🚨 不可违反的三条核心设计原则（用户 2026-04-20 敲定）

1. **爽感不能牺牲挑战性**：任何清屏/AOE/大招类技能，必须对"小怪/精英怪/BOSS"分层处理。不允许"一键无脑过关"。
2. **激光是立项差异化**：主角永远只用激光。禁止新增子弹、飞轮、炮弹、导弹等。深化激光自身（闪电球、链式、分裂、折射、词条）而非扩展武器类型。
