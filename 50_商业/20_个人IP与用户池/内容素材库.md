## 标题公式

### 数字 + 冲突

- 被 27 家发行拒绝后，我决定重新做一款游戏。
- 10 个人测试我的游戏，8 个人吐槽同一个问题。
- 7 天做一个 Demo，第一天我就发现自己想错了。

### 失败 + 反击

- 第一款游戏失败后，我不再直接写代码了。
- 被玩家骂醒后，我决定先做视频验证。
- 上一款没人玩，这次我先让陌生人骂。

### 数据 + 复盘

- 上线第一天，数据没有骗我。
- 这条视频没人想玩，我知道这个方向该砍了。
- 20 个陌生人试玩后，我改掉了核心循环。

### 技术 + 造物

- 一个 TA 做游戏，最该把技术用在哪里？
- 这 3 秒特效，是我判断方向能不能做的第一闸。
- 用 Shader 做一个“看起来就想摸”的核心玩法。

### 生活 + 游戏

- 搬到广州后，我给自己定了一个 30 天验证计划。
- 旅行不是逃避，这次我只带回一个游戏钩子。
- 独立开发最难的不是代码，是没有外部反馈。

## 内容结构

### 小红书图文

```
开头：具体数字 / 冲突 / 失败
中段：真实事件 + 具体过程
截图：开发画面、数据、评论、前后对比
结尾：一个明确动作，引导评论 / 试玩 / 进群
```

### 抖音 / 视频号

```
0-3 秒：强反差大字 + 人或实机画面
3-10 秒：直接切核心爽点
10-20 秒：一句解释 + 一个悬念
结尾：评论“试玩”/ 链接 / 预约
```

### B站 Devlog

```
1. 本周目标
2. 做出的东西
3. 遇到的问题
4. 玩家 / 数据反馈
5. 下周只改一个变量
```

## 可复用选题

### 失败复盘

- 第一款游戏为什么失败。
- 被发行拒绝后，我学会的不是坚持，而是验证。
- 我之前把朋友反馈误当市场信号。
- 如果一个方向连续两轮没人想玩，我会怎么砍。

### 产品验证

- 这个玩法 3 秒能不能看懂。
- 7 天 Demo 第 1 天：只做核心动词。
- 20 个陌生用户测试记录。
- 玩家复述卖点失败，说明我表达错了。

### 数据透明

- 本周新增了几个陌生用户信号。
- 这条内容带来了几个人进测试池。
- Demo 前 3 分钟留住了几个人。
- 广告观看次数 / 重开率 / 预约变化。

### TA 技术优势

- Shader 如何变成玩法。
- 一个特效为什么能提高点击欲望。
- 程序化生成如何降低美术成本。
- 移动端高反馈如何控制性能。

## 从 docx 提取的美妆内容结构

来源：`小红书打造人设.docx`，已于 2026-05-18 提取。

核心人设：

> 独自战斗的游戏开发者，专为女生打造“精致解压”的寻宝游戏。

当时规划的 6 周内容节奏：

| 周 | 主题 | 可复用价值 |
|----|------|------------|
| 第 1 周 起点 | 我是谁，为什么做这款游戏；30 秒 Demo 首曝 | 新项目首曝模板 |
| 第 2 周 转折 | 发行拒绝、玩家反馈、关卡 100% 有解 | 失败冲突 + 专业度 |
| 第 3 周 进化 | 听劝改美术、展示前后对比、ASMR 音效 | “听劝 + 执行力”人设 |
| 第 4 周 核心 | 收藏馆 / 梳妆台 / 样品换流量商业模式 | 商业想象必须后置 |
| 第 5 周 实战 | 微信小游戏上架、真机 Bug、Demo 上线 | 真实开发日常 |
| 第 6 周 未来 | 上线一周数据复盘、决定迭代或转下一款 | 数据驱动形象 |

可复用原则：

- 首曝必须展示核心爽点，不讲大愿景。
- 失败和拒绝要转化为“我听到了什么、改了什么”。
- 商业模式内容只能在产品数据之后讲。
- 上线或测试后必须做数据复盘。
